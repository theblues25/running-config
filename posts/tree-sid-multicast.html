Multicast บน SR-MPLS
ด้วย Tree-SID แบบ static

จากศูนย์ ถึง lab ที่ส่ง traffic ได้จริง — เริ่มจาก "multicast คืออะไร" แบบไม่ต้องมีพื้นฐาน ต่อด้วยว่าทำไม MPLS/VPN ต้องมี "ท่อ" สำหรับ multicast แล้วลงไปที่ Tree-SID ต้นไม้ multicast ที่ใช้ label ของ Segment Routing ล้วน ๆ ไม่ต้องมี LDP หรือ RSVP ในแกน ปิดท้ายด้วย lab จริงบน Nokia SR-SIM 26.7.R2 ทั้งตอนที่ทำงานปกติ ตอนลิงก์ล่ม และ gotcha ที่ไม่มีในตัวอย่างของเอกสาร

เลื่อนลงเพื่อเริ่มเรียนรู้
00 · อ่านเร็ว

สรุปสั้น ๆ ก่อนเริ่ม

  • Tree-SID คือการทำ "ต้นไม้ multicast" บน SR-MPLS โดยไม่ต้องมี mLDP หรือ RSVP-TE ในแกน ทุก node บนต้นไม้มี replication segment หนึ่งตัว ทำหน้าที่ push (ที่ราก), swap + แตกกิ่ง (กลางทาง) หรือ pop (ที่ใบ)
  • ถ้าไม่มี NSP (PCE) ต้นไม้ต้องเขียนมือ ทุก node ทุก label เราลองทำจริงบน SR-SIM 26.7.R2: root → P → leaf1/leaf2 ใน VPRN ที่ใช้ NG-MVPN (BGP auto-discovery + BGP C-multicast)
  • ผล: multicast ถึง receiver ทั้งสองฝั่ง 0% loss ทั้งบน I-PMSI และ S-PMSI และ p2mp-lsp-ping ได้คำตอบจาก leaf ครบ ตัดลิงก์ที่ไม่มี FRR แล้ว leaf2 ดับตลอดเวลาที่ลิงก์ล่ม (26 วินาที) แม้ IGP จะหาทางใหม่ได้แล้ว พอใส่ FRR (protect next-hop) ก็ไม่เห็นช่องว่างเกิน 100 ms เลย
  • เจอ gotcha ที่ไม่มีในตัวอย่างของเอกสารหลายข้อ: leaf ต้องมี "policy หลอก" ถึงจะรับได้, ช่วงสลับไป S-PMSI traffic หายไป ~22 วินาทีถ้า BGP MRAI ยังเป็นค่า default 30 วินาที, และ protect next-hop ที่ลืมผูกจะกลายเป็นกิ่งจริงจนส่งแพ็กเก็ตซ้ำ
Lab และเอกสารอ้างอิง

Lab ชื่อ mcastlab บน containerlab ทุก router เป็น Nokia SR OS 26.7.R2 (SR-SIM sr-1) เอกสารหลักที่อ้างถึงตลอดโพสต์: Multicast Routing Protocols Guide 26.7.R1 บทที่ 12 "SR P2MP policy" (ย่อว่า MRPG 12.x), MD-CLI Command Reference Guide 26.7.R1 (ย่อว่า MD-CLI ref) และ Layer 3 Services Guide 26.7.R1 (ย่อว่า L3SG)

01 · จุดเริ่มต้น

Unicast, broadcast, multicast ต่างกันอย่างไร

ลองนึกถึงการส่งของ: unicast คือส่งพัสดุถึงคนคนเดียว ถ้าจะส่งให้ 100 คนต้องแพ็ก 100 กล่อง broadcast คือประกาศเสียงตามสายให้ทั้งหมู่บ้านได้ยินไม่ว่าจะอยากฟังหรือไม่ ส่วน multicast คือรายการวิทยุ ผู้ส่งออกอากาศครั้งเดียว ใครอยากฟังก็ "จูนคลื่น" เอง แล้วเครือข่ายเป็นคนทำสำเนาตรงทางแยก เฉพาะทางที่มีคนฟังอยู่

● อยากฟัง ● ได้รับแล้ว

แอนิเมชันสลับให้ดูสามแบบ unicast: ผู้ส่งทำสำเนาเองสามชุด ลิงก์แรกแบก ×3 broadcast: ทุกเครื่องได้หมด รวมเครื่องที่ไม่อยากฟัง (ในชีวิตจริง broadcast อยู่แค่ใน subnet เดียว router ไม่ส่งข้ามไปไหน ภาพนี้แค่วางเทียบให้เห็น) multicast: ลิงก์แรกแบกแค่ ×1 แล้วไปแตกสำเนาที่ router ตรงทางแยกที่มีคนฟังเท่านั้น

01

Unicast

ผู้รับชัดเจนทีละคน ส่ง 100 คนต้องส่ง 100 รอบ ผู้ส่งเหนื่อยและท่อขาออกเต็ม

02

Broadcast

ทุกคนในวงได้หมด ใช้ได้แค่ในวงเล็ก ๆ (subnet เดียว) router ไม่ส่ง broadcast ข้ามไป

03

Multicast

ส่งครั้งเดียว เครือข่ายทำสำเนาที่ทางแยก ส่งเฉพาะทางที่มีคนอยากรับ

ข้อดีที่สำคัญที่สุดของ multicast คือผู้ส่งและลิงก์ช่วงต้นไม่ต้องแบกภาระตามจำนวนผู้รับ IPTV, ราคาหุ้นในตลาดหลักทรัพย์ และการกระจายไฟล์ firmware ใช้ multicast ด้วยเหตุผลนี้

02 · พื้นฐานที่ 1

Group address, IGMP และ (S,G)

ปลายทางของแพ็กเก็ต multicast ไม่ใช่เครื่องใดเครื่องหนึ่ง แต่เป็น group ซึ่งก็คือ IP address ช่วงพิเศษ คิดว่าเป็น "ชื่อคลื่นวิทยุ" ก็ได้

ช่วงใช้ทำอะไร
224.0.0.0/4ช่วง multicast ทั้งหมดของ IPv4 (224.0.0.0 - 239.255.255.255, RFC 5771)
224.0.0.0/24link-local control เช่น OSPF hello 224.0.0.5, PIM 224.0.0.13 ไม่ข้าม router
232.0.0.0/8Source-Specific Multicast (SSM, RFC 4607) ช่วงที่ lab นี้ใช้
239.0.0.0/8administratively scoped (RFC 2365) ใช้ภายในองค์กร คล้าย private IP ของ multicast

ฝั่ง Ethernet จะแปลง group เป็น MAC 01:00:5e:xx:xx:xx เช่นใน lab นี้ group 232.1.1.1 ออกมาเป็น 01:00:5e:01:01:01

Source, receiver และ IGMP

  • Source คือเครื่องที่ส่ง ไม่ต้อง "join" อะไรเลย แค่ส่งแพ็กเก็ตไปที่ group
  • Receiver คือเครื่องที่อยากรับ ต้องบอก router ที่อยู่ใกล้ที่สุดว่า "ฉันอยากรับ group นี้" ผ่านโปรโตคอล IGMP (Internet Group Management Protocol, IPv4) หรือ MLD (IPv6)
  • IGMPv2: "ฉันอยากรับ group G" (ไม่สนว่าใครส่ง)  ·  IGMPv3 (RFC 3376): "ฉันอยากรับ group G จาก source S เท่านั้น" ซึ่งเป็นสิ่งที่ SSM ต้องการ

ใน lab นี้ receiver ใช้ iperf -s -u -B 232.1.1.1 -H 192.168.10.10 ซึ่งทำให้ Linux ส่ง IGMPv3 join แบบ (S,G) ออกไป

● ข้อความ join ● กิ่งของต้นไม้

receiver "ยกมือ" ด้วย IGMP แล้ว router ส่ง Join ย้อนขึ้นไปหาต้นทางทีละ hop ทุก router ที่ Join ผ่านจะจดว่า "ขาที่ join มาคือขาออก" ต้นไม้จึงงอกขึ้นมาเองทีละกิ่ง และ router ที่มี state ของ group นั้นอยู่แล้วไม่ต้องส่ง Join ขึ้นไปซ้ำ

(S,G) กับ (*,G)

  • (S,G) อ่านว่า "S comma G" คือ traffic จาก source S ไป group G เส้นทางเดินจาก S ตรงมาหา receiver (shortest-path tree)
  • (*,G) คือ traffic ไป group G จากใครก็ได้ ต้องมีจุดนัดพบกลางที่เรียกว่า RP (Rendezvous Point) ให้ source กับ receiver มาเจอกัน โหมดนี้เรียกว่า ASM (Any-Source Multicast)

SSM ใช้แค่ (S,G) ไม่ต้องมี RP เลย จึงง่ายกว่ามาก lab นี้เลือก SSM ด้วยเหตุผลนี้

03 · พื้นฐานที่ 2

RPF กฎกันลูป และ PIM ในหนึ่งย่อหน้า

unicast ตัดสินว่า "จะส่งไปทางไหน" จากปลายทาง แต่ multicast คิดกลับด้าน: router ดูว่าแพ็กเก็ต "มาจากทางไหน" แล้วถามตัวเองว่า "ถ้าจะส่ง unicast กลับไปหา source ฉันจะออกขาไหน" ถ้าแพ็กเก็ตเข้ามาทางขานั้นก็รับ ถ้าเข้ามาขาอื่นก็ทิ้ง กฎนี้เรียกว่า RPF (Reverse Path Forwarding) และเป็นหัวใจที่กันไม่ให้ multicast วนลูป

ใน MVPN คำถาม RPF จะกลายเป็น "PE ตัวไหนอยู่ต้นทางของ source" ซึ่งเราจะเห็นใน output ของ lab เป็นบรรทัด Rpf Neighbor : 10.0.0.1 และ Incoming Intf : mpls-if-73728

PIM (Protocol Independent Multicast)

PIM คือโปรโตคอลที่ router คุยกันเพื่อสร้างต้นไม้ multicast คำว่า "protocol independent" แปลว่ามันไม่มีตาราง routing ของตัวเอง แต่ยืม unicast routing table (จาก OSPF/IS-IS/BGP อะไรก็ได้) มาใช้ทำ RPF แล้วส่ง Join/Prune ทีละ hop ย้อนจาก receiver ขึ้นไปหา source (หรือ RP) แบบที่เห็นในแอนิเมชันของข้อ 02 ใน lab นี้ PIM ทำงานเฉพาะขอบ (ฝั่งลูกค้าใน VPRN) ส่วนแกนกลางไม่มี PIM เลย

04 · ปัญหาที่ตามมา

ทำไม multicast ใน MPLS/VPN ต้องมี "provider tunnel"

ใน L3VPN (VPRN) ปกติ แกนกลาง (P router) ไม่รู้จัก route ของลูกค้าเลย มันรู้แค่ label PE ห่อแพ็กเก็ตลูกค้าด้วย label แล้วส่งผ่านแกน วิธีนี้ทำงานดีมากกับ unicast แต่ multicast ต้องทำสำเนาระหว่างทาง ถ้าแกนไม่รู้จัก group ของลูกค้า แล้วจะทำสำเนาที่ไหน?

ทางที่ง่ายที่สุดคือให้ PE ต้นทางทำสำเนาเองแล้วยิง unicast ไปหา PE ปลายทางทุกตัว (ingress replication) แต่นั่นก็คือการกลับไปเป็น unicast 100 กล่องในข้อ 01 ทางที่ดีกว่าคือสร้างท่อ point-to-multipoint (P2MP) ในแกนที่แกนรู้จักในระดับ label: แพ็กเก็ตเข้าที่ราก แตกกิ่งที่ P แล้วไปออกที่ PE ปลายทางหลายตัว ท่อนี้เรียกว่า provider tunnel หรือ PMSI (P-Multicast Service Interface)

● แพ็กเก็ตลูกค้า ● ท่อ P2MP

PE1 ห่อแพ็กเก็ตลูกค้าเข้าท่อ P2MP, P ทำสำเนาตาม label โดยไม่ต้องรู้จัก group ของลูกค้าเลย แล้ว PE2/PE3 แกะห่อส่งต่อให้ลูกค้า

05 · กลไกที่ 1

NG-MVPN แบบภาษาคน

NG-MVPN (RFC 6513/6514) คือชุดกติกาที่ PE ใช้ BGP คุยกันเรื่อง multicast ในแต่ละ VPN แทนการวิ่ง PIM ข้ามแกน ของหลัก ๆ มีสามอย่าง

ชื่อเปรียบเทียบBGP route ที่เกี่ยวข้อง
I-PMSI (Inclusive)"ท่อรวม" ของ VPN นี้ ไปหา PE ทุกตัว ใน VPNIntra-AS I-PMSI A-D route (route type 1)
S-PMSI (Selective)"ท่อเฉพาะ" สำหรับ (S,G) ตัวใดตัวหนึ่ง ควรไปหาเฉพาะ PE ที่มีคนรับS-PMSI A-D route (type 3) และ Leaf A-D route (type 4)
C-multicast route"join ของลูกค้า" ที่ PE ปลายทางส่งกลับไปบอก PE ต้นทาง แทน PIM joinSource Tree Join (type 7)
● ท่อรวม I-PMSI ● ท่อเฉพาะ S-PMSI
  1. ① PE ทุกตัวประกาศ Intra-AS I-PMSI A-D ว่า "ฉันอยู่ใน VPN นี้" PE ต้นทางแนบ PMSI Tunnel Attribute (PTA) บอกว่า "ท่อรวมของฉันคือท่อชนิดนี้ เลขนี้"
  2. ② receiver ส่ง IGMP ให้ PE ปลายทาง PE ปลายทางหาว่า source อยู่หลัง PE ไหน (RPF ผ่าน VPN route) แล้วส่ง C-multicast Source-Join ไปหา PE นั้น
  3. ③ PE ต้นทางเอา traffic (S,G) ใส่ท่อ I-PMSI
  4. ④ ถ้า traffic แรงเกิน threshold PE ต้นทางจะย้าย (S,G) นั้นไปท่อ S-PMSI โดยประกาศ S-PMSI A-D แล้ว PE ที่สนใจตอบด้วย Leaf A-D
06 · เลือกใช้อะไร

ตัวเลือกของ provider tunnel บนแกน SR

ถ้าแกนกลางเป็น SR-MPLS อยู่แล้ว ท่อ multicast ทำได้หลายแบบ แต่ละแบบแลกกับสิ่งที่ต้องเปิดเพิ่มในแกนต่างกัน

ตัวเลือกทำงานอย่างไรต้องมีอะไรเพิ่มในแกนหมายเหตุบน SR OS 26.7
Ingress Replication PE ต้นทางทำสำเนาเอง ยิง unicast ไม่ต้อง ง่ายสุด แต่ลิงก์ขาออกของ root รับภาระตามจำนวน PE และไม่มีใน provider-tunnel ของ VPRN NG-MVPN บน 26.7 (MD-CLI ref ระบุว่า inclusive เลือกได้แค่ bier, mldp, p2mp-sr, pim, rsvp)
mLDP ต้นไม้ P2MP สร้างจาก LDP LDP ทุก node ถ้าแกนเป็น SR ล้วน ก็ต้องเปิด LDP กลับมาเพื่อ multicast อย่างเดียว
RSVP-TE P2MP ต้นไม้แบบ TE จาก RSVP RSVP ทุก node state ต่อ LSP ในแกนเยอะ
BIER header บอก "bit ของ PE ปลายทาง" แกนไม่มี state ต่อ flow เลย BIER ใน IGP ต้อง FP4/FP5 และไม่รองรับบน 7250 IXR (MRPG บทที่ 11)
Tree-SID ต้นไม้ P2MP ที่ใช้ label จาก SR แต่ละ node บนต้นไม้มี replication segment ไม่ต้องมี LDP/RSVP แต่ต้องมี "คนวางต้นไม้" (PCE หรือคนเขียนมือ) static ด้วย CLI หรือ NSP ผ่าน PCEP (MRPG 12.4.1, 12.4.2)
07 · กลไกที่ 2

Tree-SID: policy ที่ราก กับ replication segment ทุก node

Tree-SID มาจาก draft ของ IETF กลุ่ม SR P2MP policy (draft-voyer-pim-sr-p2mp-policy, draft-voyer-spring-sr-replication-policy ฯลฯ ดูรายชื่อเต็มใน MRPG 12) แก่นของมันคือการแยกของออกเป็นสองชั้น

01

P2MP policy

อยู่ที่ root เท่านั้น ระบุตัวด้วยคู่ <root-address, tree-id> บอกว่า "ต้นไม้นี้คือต้นไหน" แต่ไม่มีข้อมูล forwarding เลย (MRPG 12.1)

02

Replication segment

อยู่บนทุก node ของต้นไม้ คือคำสั่ง forwarding จริง: "รับ label X แล้วทำสำเนาออกขา A ด้วย label Y และขา B ด้วย label Z" (MRPG 12.2)

03

Key ร่วม

replication segment แต่ละตัวถูกระบุด้วย <tree-id, root-address, instance-id> (MRPG 12.4.1) ทุก node ของต้นเดียวกันต้องใช้ค่าเดียวกัน

บทบาทsid-actionทำอะไร
Rootpushรับแพ็กเก็ตจาก VPRN ติด label ของกิ่งแรก แล้วส่งออก
Transitswapรับ label ขาเข้า (incoming-sid) ทำสำเนาตามจำนวน downstream-nodes แล้วเปลี่ยน label เป็นของกิ่งถัดไป
Leafpopถอด label แล้วส่งให้ VPRN ที่ผูกกับต้นไม้นี้

ค่าที่เลือกได้ของ sid-action คือ none/push/pop/swap ตาม MD-CLI ref (replication-segment ... segment-routing-mpls sid-action)

09 · ลงลึกอีกนิด

tree-id, candidate path และ instance

  • tree-id: เลขประจำต้นไม้ (ต่อ root) ช่วงที่ใช้ได้คือ 8193-16286 (MD-CLI ref, p2mp-policy tree-id) เลขนี้ถูกแนบไปใน BGP PTA ให้ leaf รู้ว่า "ท่อของ VPN นี้คือต้นไม้ <root, tree-id>" และไม่ได้สร้างอัตโนมัติ มาจากค่าที่เราใส่ใน policy (MRPG 12.4.1.2)
  • candidate path (CP): ต้นไม้หนึ่งต้นมีได้หลายทางเลือก ตัวที่ preference สูงสุดและ oper up จะถูกใช้งาน ทำหน้าที่เป็น tree redundancy (MRPG 12.1, 12.4.4.1)
  • path instance: ใน CP หนึ่งมีได้หลาย instance (แต่ละตัวคือ P2MP LSP หนึ่งต้น) ใช้ทำ make-before-break ตอน re-optimize: สร้าง instance ใหม่ให้ครบทั้งต้นก่อน แล้วค่อยสลับ active-instance (MRPG 12.4.9)
● instance ที่ active ● กำลังสร้าง

make-before-break: instance ใหม่ต้องมี replication segment ครบทุก node ก่อน แล้วจึงสลับ active-instance (ภาพนี้อธิบายแนวคิดตาม MRPG 12.4.9 ส่วนใน lab ใช้แค่ instance 1)

10 · ทำไม static

ทำไม "static" ในงานนี้ และ NSP จะเพิ่มอะไรให้

SR OS สร้าง P2MP policy ได้สองแบบ (MRPG 12.4): static ด้วย CLI ที่เราเขียน policy ที่ root และ replication segment บนทุก node เอง หรือ PCE (NSP) ผ่าน PCEP ที่ root เรียนรู้ leaf จาก BGP MVPN (Leaf A-D ฯลฯ) แล้วรายงานไปให้ PCE จากนั้น PCE คำนวณต้นไม้จาก topology (BGP-LS) แล้วดาวน์โหลดทั้ง policy และ replication segment ลงทุก node ให้เอง (MRPG 12.4.2)

ถ้าไม่มี NSP ก็เหลือทางเดียวคือ static และสิ่งที่หายไปเมื่อไม่มี PCE คือ:

  • ต้นไม้ไม่โตตาม receiver: BGP Leaf A-D ไม่ได้ทำให้เกิดกิ่งใหม่ static S-PMSI หนึ่งต้นใช้ร่วมกันทุก (S,G) ที่ข้าม threshold (MRPG 12.4.1.1)
  • ไม่มี re-optimization อัตโนมัติ: ลิงก์ล่มแล้ว IGP หาทางใหม่ได้ แต่ต้นไม้ไม่ขยับ (เราจะเห็นในข้อ 16)
  • FRR, การ re-optimize (instance ใหม่ + MBB) และ CP สำรอง ต้องเขียนเองทั้งต้น
  • PCE ฝั่ง SR OS เอง เท่าที่เอกสารระบุไว้ ไม่ได้ทำ P2MP ให้ (ฝั่ง PCC พูด draft-dhs-spring-pce-sr-p2mp-policy-00 ตาม L3SG ส่วน standards) ในทางปฏิบัติจึงหมายถึง NSP

17 · ข้อควรระวัง

Gotchas ที่เจอจริงใน lab

1 · Leaf ต้องมี "provider tunnel หลอก" ถึงจะรับได้

ตัวอย่างใน MRPG 12.4.3 แสดง MVPN เฉพาะฝั่ง root ใน lab ลองไล่ดังนี้:

  • leaf ที่ไม่มี provider-tunnel เลย: ได้ IGMP join, ได้ Intra-AD ของ root (PTA ถูกต้อง) แต่ PIM ค้าง Resolved By : unresolved ไม่มี tunnel interface และไม่ส่ง Source-Join
  • เพิ่ม mdt-type receiver-only อย่างเดียว: ยังเหมือนเดิม
  • ใส่ inclusive p2mp-sr admin-state enable โดยไม่มี policy: commit ไม่ผ่าน MGMT_CORE #3001 ... inclusive p2mp-sr static-policy-mpls or static-policy-srv6 is missing
  • ทางที่ใช้ได้: สร้าง p2mp-policy "IPMSI-LOCAL" (root = ตัวเอง, tree-id 9100, ไม่มี CP) แล้วชี้ static-policy-mpls ไปที่มัน พร้อม mdt-type receiver-only ทันทีที่ commit leaf ได้ Rx-IPMSI จาก 10.0.0.1 และ RPF resolve

ข้อควรระวัง: เรื่อง sender-only/receiver-only ใน L3SG 3.4.7.7 ระบุว่ารองรับกับ provider tunnel แบบ RSVP-TE และ LDP ไม่ได้พูดถึง p2mp-sr ผลที่เห็นนี้จึงเป็นพฤติกรรมของ 26.7.R2 บน SR-SIM ที่ยังไม่มีเอกสารยืนยัน ควรถาม Nokia ก่อนใช้งานจริง (นอกจากนี้ option p2mp-policy-mpls ที่ MD-CLI ref มีใน inclusive p2mp-sr ไม่มีให้ใช้บน image 26.7.R2 ที่ทดสอบ ตอบ Unknown element)

2 · แผน label คือทุกอย่าง

ไม่มีอะไรเตือนถ้า replication-sid ของ upstream ไม่ตรงกับ incoming-sid ของ downstream ต้นไม้จะ "Up" ทุกจุด แต่กิ่งนั้นไม่มี traffic ทางป้องกัน: ใช้สูตร label ที่อ่านแล้วรู้ว่าเป็นของต้นไหน node ไหน เก็บตาราง label คู่กับ config และรัน p2mp-lsp-ping หลังแก้ทุกครั้ง

3 · next-hop ต้องต่อตรง

next-hop-address ของ downstream ต้องเป็น interface ของเพื่อนบ้านที่ต่อตรง (ถ้าไม่ใช่ unnumbered) ใส่ loopback ไม่ได้ (MRPG 12.4.13) ถ้าจะข้าม node ที่ไม่รองรับ replication ให้ใช้ SID list (MRPG 12.5) และเมื่อใช้ SID list หลายตัวห้ามใส่ next-hop-address ไม่งั้น commit ไม่ผ่านด้วย TREE_SID #3016 ... can configure either next-hop address/name or Sid-List

4 · ไม่มี re-optimization อัตโนมัติ และ root มองไม่เห็นปัญหากลางทาง

Test 3 แสดงชัดว่า IGP หายใจได้แต่ต้นไม้ไม่ และ root ยัง Up/Up ถ้าจะ re-route ต้นไม้ต้องสร้าง instance ใหม่ครบทั้งต้นแล้วสลับ active-instance (MRPG 12.4.9) ต้องมี monitoring ที่ไม่พึ่งสถานะที่ root เช่นรัน p2mp-lsp-ping เป็นระยะ หรือดู downstream-nodes บนทุก transit

5 · FRR: link protection เท่านั้น และ protect next-hop ที่ไม่ได้ผูกจะกลายเป็นกิ่งจริง
  • รองรับเฉพาะ facility bypass แบบ link protection ไม่มี node protection (MRPG 12.4.5) และถ้า node หนึ่งมี replication segment ที่พึ่ง protection tunnel เยอะ เวลา FRR อาจเกิน 50 ms (MRPG 12.4.13)
  • ตอนกลับสู่ทางหลัก doc บอกว่าอาจมี outage สั้น ๆ และจะกลับเมื่อ ARP ของ next-hop หลักพร้อม (MRPG 12.4.6) ใน lab ไม่เห็นช่องว่างเกิน 100 ms
  • gotcha ที่เจอจริง: ถ้า downstream-nodes 3 ยังอยู่แต่ลบ protect-nexthop-id 3 ออก มันจะกลายเป็นกิ่งปกติทันที leaf2 ได้ทุกแพ็กเก็ตสองครั้ง (rcv2 วัดได้ 100 pps จากสตรีม 50 pps, IP id ซ้ำ, TTL ต่างกัน 1 เพราะสำเนาที่อ้อมผ่าน leaf1 ผ่านมากกว่าหนึ่ง hop) ตอนถอด FRR จึงต้องลบหรือ disable downstream ตัวสำรองด้วย

  • ดักแพ็กเก็ตบนพอร์ตของ SR-SIM ไม่ได้: tcpdump ใน network namespace ของ node SR-SIM เห็น 0 แพ็กเก็ตแม้ traffic วิ่งอยู่ จึงไม่มีภาพ label บนสาย หลักฐานเรื่อง label ทั้งหมดมาจาก show command ของ SR OS และ counter
  • เวลาที่วัด (FRR, switchover) เป็นของ SR-SIM ใช้เทียบ "มี/ไม่มีช่องว่าง" ได้ แต่ไม่ใช่ตัวเลข convergence ของ hardware
  • datapath multicast ของ Tree-SID บน SR-SIM ทำงานจริง (ต่างจาก SRv6 VPN datapath ที่เคยทดสอบในโพสต์ก่อนแล้วไม่ forward) ข้อนี้เป็นข่าวดีสำหรับคนที่อยากลองเอง
19 · สรุป

รวมทุกอย่างเข้าด้วยกัน

  • Multicast ส่งครั้งเดียวแล้วให้เครือข่ายทำสำเนาที่ทางแยก receiver บอกความต้องการด้วย IGMP และ router กันลูปด้วย RPF
  • ใน MPLS/VPN แกนไม่รู้จัก group ของลูกค้า จึงต้องมี provider tunnel (PMSI) และ NG-MVPN ใช้ BGP แทน PIM ข้ามแกน: Intra-AD + PTA, Source-Join, S-PMSI A-D + Leaf A-D
  • Tree-SID ทำให้แกน SR-MPLS ทำ multicast ได้โดยไม่ต้องเปิด LDP หรือ RSVP กลับมา โครงสร้างเข้าใจง่าย: policy ที่ root บอกว่าต้นไหน, replication segment ทุก node บอกว่าจะทำสำเนาอย่างไร (push / swap / pop)
  • แบบ static ใช้ได้จริง traffic ไหลถูกต้องทั้ง I-PMSI และ S-PMSI แต่ทุกอย่างที่ "อัตโนมัติ" ใน multicast แบบเดิม (ต้นไม้โตตามผู้รับ, re-route ตาม IGP, ตัดกิ่งที่ไม่มีคนรับ) หายไปหมด และต้องเขียนเองทุก node ทุก label
  • เหมาะกับ: ต้นไม้ไม่กี่ต้น topology นิ่ง จำนวน PE ไม่เยอะ (เช่น IPTV ที่ส่งไปทุก PE อยู่แล้ว หรือ lab/POC) และควรมี FRR บนทุกกิ่งสำคัญ
  • ถ้าต้นไม้เยอะหรือผู้รับเปลี่ยนบ่อย ควรมองไปที่ NSP (PCE) หรือเทคโนโลยีอื่นตามตารางในข้อ 06
