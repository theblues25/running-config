วัด delay ราย member ของ LAG
ด้วย STAMP บน SR OS

LAG หนึ่งก้อนมีหลาย member แต่ STAMP แบบเดิมวัดได้แค่เส้นเดียว บทนี้เทียบ 3 วิธีวัด delay บน LAG ใน SR OS 26.7.R2 ว่าวิธีไหนเห็นค่าราย member วิธีไหนส่งค่าเข้า IS-IS และ Flex-Algo ได้จริง พร้อม config ที่ copy ไปใช้ได้ ขั้นตอนตรวจสอบทีละโหมด และวิธี apply ทั้ง network ด้วย configuration group

ผลทั้งหมดมาจาก lab SR-SIM 26.7.R2 และใส่ delay ด้วย netem

TL;DR

  • บน LAG ถ้าใช้ link measurement แบบเดิม (single session) test packet จะถูก hash ลง member เดียว ใน lab ใส่ delay 5 ms ไว้ที่ member ที่ไม่ถูก hash แล้วค่าที่วัดได้และค่าที่ IS-IS โฆษณา ไม่ขยับเลย
  • SR OS 26.7.R2 วัด delay บน LAG ได้ 3 แบบ:
    1. Single session ใช้มาตั้งแต่แรก เข้า IS-IS ได้ แต่เห็นแค่ member ที่ถูก hash
    2. lag-micro-sessions true (เริ่มมีใน 26.3.R1, default false) ยิง STAMP แยกทีละ member แล้วรวมเป็นค่าเดียวด้วย min / max / avg / max-of-min / min-of-max จากนั้นส่งเข้า IS-IS
    3. LAG IP Measurement ได้ค่าละเอียดราย member (RT delay, IFDV, FLR) แต่ใช้เป็น telemetry อย่างเดียว routing ไม่เห็นค่านี้ และลิงก์นั้นจะหลุดออกจาก Flex-Algo แบบ delay
  • IS-IS ส่งออกไป ค่าเดียวต่อ adjacency (ASLA, Delay Min = Max) ไม่มีข้อมูลราย member ออกไปนอกกล่อง
  • ถ้าใช้ configuration group ให้ apply group เดียวไว้ที่ router "Base" (template + twamp-light) แล้วใส่ lag-micro-sessions true แบบ local บรรทัดเดียว บนทุก interface ที่อยู่บน LAG อย่าใส่ true ไว้ใน group เพราะ interface ที่อยู่บน port จะ commit ผ่าน แต่หยุดวัดไปเงียบ ๆ และค่าเก่าจะค้างอยู่ใน LSP
  • กับดักใหญ่สุด: lag-micro-sessions + delay min + มี aggregate-sample-window threshold จะทำให้ค่าที่โฆษณา สลับไปมาระหว่าง 0.4 กับ 2.9 ms ทุก ~15 วินาที

ปัญหาของ LAG

  • link measurement เดิมสร้าง test session 1 ตัวต่อ IP interface เอกสาร (OAM and Diagnostics Guide 26.7.R1, 5.1.1) เขียนไว้ว่า "If the IP interface is configured over a LAG, the test session is hashed to a single Ethernet port"
  • ขาไปใช้ hash ของ sender ขากลับใช้ hash ของ reflector ต่างฝั่งต่าง hash
  • ใน network ของ SP member แต่ละเส้นของ LAG ไม่จำเป็นต้องเท่ากัน เช่น member หนึ่งถูก DWDM protection ย้ายไปวิ่งอีกเส้นทาง ถ้าวัดได้แค่ member ที่ถูก hash Flex-Algo ก็จะเชื่อค่าของ member นั้น ทั้งที่ traffic อีกครึ่งที่ hash ไปอีก member อาจช้ากว่าหลายเท่า

สามโหมดบน LAG ทำงานต่างกันอย่างไร

โหมด 1: single session (แบบเดิม)

  • 1 session ต่อ IP interface ซึ่ง LAG จะ hash ลง member เดียว
  • ค่าที่ได้คือค่าของ member ที่ถูก hash แล้วส่งไป routing engine เป็น interface delay ตามปกติ
  • show ไม่บอก ว่าใช้ member ไหน (detail บอกแค่ LAG Name ไม่มีบรรทัด port)

โหมด 2: link measurement + lag-micro-sessions

  • เปิดด้วย if-attribute delay dynamic link-measurement lag-micro-sessions true (default false)
  • ระบบสร้าง micro-session ให้แต่ละ member เอง แต่ละตัวมี STAMP Session ID และ Micro-session ID แยกกัน (RFC 9534) packet ถูกส่งลง member นั้นตรง ๆ และ reflector ตอบกลับทาง member เดิม
  • ทุกครั้งที่ window ของ member ใดปิด ค่าของ member นั้นจะถูก "promote" ไปเทียบกับค่าล่าสุดของ member อื่นตาม delay ใน template ค่าที่ชนะจะไป routing engine พร้อมกับ Measurement Source ที่บอกว่ามาจาก member ไหน
  • IS-IS ยังโฆษณา ค่าเดียวต่อ adjacency เหมือนเดิม

โหมด 3: LAG IP Measurement

  • ใช้คนละ template คือ test-oam lag-ip-measurement lag-ip-measurement-template และผูกที่ if-attribute delay dynamic lag-ip-measurement
  • วัด round trip ราย member ได้ frame delay (FD), IFDV และ frame loss ratio (FLR) ต่อ sample window
  • OAM Guide 26.7.R1, 5.1: "LAG IP Measurement does not report delay metrics to the routing engine. Instead, it focuses on reporting statistics to a northbound system."
  • ใช้บน interface เดียวกับโหมด 1/2 ไม่ได้ (PIP #4083 ดูหัวข้อ Gotchas)

Lab และ config พื้นฐาน

  • Nokia SR-SIM 26.7.R2 (sr-1) ทั้ง 3 ตัว รันบน containerlab ทุก LAG ใช้ LACP active
  • interface ใช้ชื่อตามเพื่อนบ้าน: r1 มี to-r2 (lag-12) กับ to-r3 (lag-13), r2 มี to-r1 กับ to-r3 (lag-23), r3 มี to-r1 กับ to-r2
  • netem ใส่ทิศเดียว (5 ms) พอใช้ unidirectional-measurement derived (RTT/2) จะเห็นเพิ่มขึ้นประมาณ 2.5 ms ทั้งสองฝั่ง ลิงก์ปกติบน SR-SIM วัดได้ราว 350–550 us
  • ส่วนเรื่อง aggregation และ config group ใช้ lab ย่อยแยกอีก 2 ชุด (อธิบายในหัวข้อนั้น)

ควรเลือกแบบไหน

  • min เป็นค่าที่มองโลกในแง่ดีที่สุด (เท่ากับที่โหมด 1 ได้ถ้าบังเอิญ hash ลง member ที่เร็ว) Flex-Algo จะไม่รู้เลยว่ามี member ช้า
  • max ปลอดภัยสุดสำหรับ service ที่มี SLA เรื่อง latency เพราะ traffic ส่วนหนึ่งวิ่งบน member ที่ช้าจริง แต่จะถูก jitter ชั่วขณะของ member ใด member หนึ่งดึงขึ้นได้ง่าย
  • max-of-min ในความเห็นของเราเป็นตัวเลือกที่สมดุล: สะท้อน member ที่ช้า แต่ใช้ค่า floor ของแต่ละ member จึงทน jitter spike ได้ดีกว่า max (ใน lab 2871 เทียบกับ 3455 us)
  • avg ได้ตัวเลขที่ไม่ตรงกับ member ไหนเลย ใช้ได้ถ้าต้องการค่าเฉลี่ยแบบคร่าว ๆ
  • min-of-max เป็นการดูเพดานของ member ที่ดีที่สุด ซึ่งใกล้กับ min ในทางปฏิบัติ

Apply ด้วย configuration group

โจทย์

network ของ SP ส่วนใหญ่ apply STAMP ให้ core interface ทุกตัวด้วย group เดียวที่ match ชื่อด้วย regex แต่ core interface มีทั้งแบบที่อยู่บน LAG และแบบที่อยู่บน port เดี่ยว เราต้องการให้ LAG ใช้ micro-session และให้ port ใช้ session ปกติ

  • group ของ SR OS เลือก interface จากชื่อ (list key) ด้วย regex มันไม่รู้ว่า interface อยู่บน LAG หรือ port (MD-CLI User Guide 26.7.R1, 4.13.1.2)
  • config ที่ใส่ local ไว้ ชนะ ค่าที่ inherit มาจาก group เสมอ (MD-CLI UG 4.13.3)
  • lag-micro-sessions มี default เป็น false อยู่แล้ว

lab ย่อย: r1–r2 มี lag-1 (c1, c2, ใส่ netem 5 ms ที่ c2) เป็น interface to-core-rX-lag1 และ port 1/1/c3/1 (ใส่ netem 3 ms) เป็น interface to-core-rX-c3 template ใช้ delay avg และไม่มี aggregate threshold

Pattern ที่แนะนำ: group เดียว + local override บน LAG

  • ไม่ต้องใส่ lag-micro-sessions false ใน group เพราะ default เป็น false อยู่แล้ว ใน lab ใส่ false ไว้ใน group ด้วย (เลยเห็นบรรทัด ## inherited ... false ใน output ข้างล่าง) ผลออกมาเหมือนกัน ถ้าอยากให้อ่านแล้วเข้าใจง่ายจะใส่ไว้ก็ได้
  • ถ้าลืมใส่ local บน LAG ใหม่ ผลที่ได้คือ single session แบบเดิม ซึ่งยังมี delay ส่งเข้า IS-IS ตามปกติ ไม่มีอะไรพัง
  • ถ้าฝั่งตรงข้ามยังไม่รองรับ micro-session (vendor อื่นหรือ release ก่อน 26.3) ก็ไม่ต้องใส่ local บน LAG นั้น เลือกเปิดทีละ LAG ได้

C. แยกเป็น 2 group ตามชื่อ interface

Gotchas (ส่วนใหญ่เงียบ ไม่มี error)

  • ไม่มี advertise-delay true หรือไม่มี ASLA วัดได้ปกติแต่ไม่มี delay ใน LSP (มีแค่ Adj-SID)
  • ไม่มี twamp-light reflector prefix ที่ครอบ IP ของฝั่งตรงข้าม session ขึ้น Up แต่ได้ Rcv/Snt 0/5
  • ค่า ASLA จะขึ้นก็ต่อเมื่อ เปิด SR และ Flex-Algo participate แล้ว
  • aggregate threshold + lag-micro-sessions + delay min ค่าที่โฆษณาสลับระหว่าง ~0.4 กับ ~2.9 ms ทุก ~15 วินาที (รายละเอียดข้างล่าง)
  • lag-micro-sessions true บน interface ที่อยู่บน port commit ผ่าน แต่ Oper Down, InterfaceNotLag และค่าเก่าค้างอยู่ใน LSP
  • LAG IP Measurement + link-measurement บน interface เดียวกัน ใส่ทีละบรรทัดได้ แต่จะตกตอน validate/commit:

  • ถ้าค่าที่ report แกว่ง ลองใช้ isis interface delay-normalization ช่วย (มีตั้งแต่ 24.10 ตาม RN)
