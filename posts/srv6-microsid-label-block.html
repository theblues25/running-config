SRv6 Micro-SID

SRv6 ถูกพูดถึงว่าไม่ต้องพึ่ง MPLS อีกต่อไป — ที่อยู่ปลายทางแบบ IPv6 บอกทุกอย่างที่ต้องรู้ในตัวเองอยู่แล้ว แต่พอไปเปิดคอนฟิกจริงบน Nokia SR OS ของฟีเจอร์ที่ชื่อ Micro-SID กลับเจอคำว่า mpls-labels, reserved-label-block โผล่มาเต็มไปหมด หน้านี้จะพาไปดูตั้งแต่พื้นฐานว่าทำไมถึงเป็นแบบนั้น ไปจนถึงลองลากเลื่อนดูการแบ่ง GIB/LIB เองและดูแพ็กเก็ตเดินทางทีละ hop จริง — เริ่มจากศูนย์ ไม่ต้องมีพื้นฐาน SRv6 มาก่อน

เลื่อนลงเพื่อเริ่มเรียนรู้
01 · จุดเริ่มต้น

Segment Routing คืออะไร (ไม่ต้องรู้ MPLS มาก่อน)

เครือข่ายแบบเดิม แต่ละเราเตอร์ต้อง "เดาทาง" เองทีละ hop — เหมือนถามทางที่สี่แยกไปเรื่อย ๆ จนถึงปลายทาง Segment Routing เปลี่ยนวิธีคิดใหม่: ให้เราเตอร์ต้นทางเขียน "รายการจุดแวะ" ทั้งหมดแนบไปกับแพ็กเก็ตตั้งแต่แรก แต่ละเราเตอร์ระหว่างทางแค่เปิดดูจุดแวะถัดไปในรายการแล้วส่งต่อ ไม่ต้องเดาเองเลย

01

ต้นทางตัดสินใจ

เราเตอร์ต้นทางเลือกเส้นทางทั้งหมดล่วงหน้า ไม่ปล่อยให้แต่ละจุดตัดสินใจเอง

02

รายการฝังไปกับแพ็กเก็ต

"จุดแวะ" (segment) ทุกจุดถูกเขียนแนบไปกับแพ็กเก็ตเอง ไม่ต้องมีใครจำเส้นทางไว้ล่วงหน้า

03

แต่ละจุดทำตามคิวถัดไป

เราเตอร์ระหว่างทางแค่มองจุดแวะถัดไปในรายการ ทำตามแล้วส่งต่อ ไม่ต้องคิดอะไรเพิ่ม

02 · พื้นฐานที่ 1

SRv6 เอา "จุดแวะ" ไปฝังไว้ในที่อยู่ IPv6 เลย

จากแนวคิด "ฝังรายการจุดแวะไปกับแพ็กเก็ต" ในข้อที่แล้ว คำถามต่อมาคือ — แต่ละจุดแวะจะเก็บด้วยอะไร? SRv6 (Segment Routing over IPv6) เลือกวิธีที่ตรงไปตรงมาที่สุด: ให้ จุดแวะแต่ละจุดคือที่อยู่ IPv6 หนึ่งตัวเลย ไม่ต้องมีเลข label แยกต่างหากแบบ MPLS รายการจุดแวะทั้งหมดถูกเก็บไว้ใน SRH (Segment Routing Header) ซึ่งเป็น IPv6 extension header ที่อยู่ต่อจาก IPv6 header ทันที ก่อนถึง payload (ไม่ใช่ต่อท้ายแพ็กเก็ต) และที่อยู่ IPv6 แต่ละตัวยังแบ่งเป็น 2 ส่วนในตัวมันเอง: Locator (เราเตอร์ไหน) และ Function (ทำอะไรที่นั่น)

● Locator (เราเตอร์ไหน) ● Function (ทำอะไร)

แพ็กเก็ตพกรายการจุดแวะทั้งหมดไว้ใน SRH เหมือนเดิมตลอดเส้นทาง (สี่เหลี่ยมเล็ก ๆ ด้านบนแทนตัวนับ Segments Left ที่เหลืออยู่ ไม่ใช่รายการที่ถูกตัดทิ้ง) ทุกครั้งที่ผ่านเราเตอร์หนึ่งตัว ค่า Segments Left จะลดลง 1 แล้วที่อยู่ปลายทาง (DA) จะถูกเปลี่ยนให้ชี้ไปยังจุดแวะถัดไปในรายการเดิม — รายการใน SRH เองไม่ได้ถูกลบออกจริง ยกเว้นเปิดใช้ PSP/USP ที่อนุญาตให้ตัด header ทิ้งตอนถึงจุดท้าย ๆ

03 · ปัญหาที่ตามมา

ยิ่งเส้นทางซับซ้อน ยิ่งต้องแบกรายการยาว

วิธีของ SRv6 ที่เพิ่งเห็นไปเรียบง่ายดี แต่แลกมาด้วยต้นทุนที่มองข้ามไม่ได้: ที่อยู่ IPv6 หนึ่งตัวยาวถึง 128 บิต ถ้าเส้นทางหนึ่งต้องผ่าน 6 จุดแวะ ก็ต้องแนบที่อยู่ 6 ตัวเต็ม ๆ ไปกับทุกแพ็กเก็ต — ยิ่งเครือข่ายใหญ่ ยิ่งทำ traffic engineering ซับซ้อน รายการนี้ก็ยิ่งยาว กินพื้นที่และแรงประมวลผลทุก hop

● ขนาด SRH ที่ต้องแบก

ยิ่งจำนวนจุดแวะเพิ่ม แท่งกราฟ (ขนาด header ที่ต้องแบก) ก็ยิ่งยาวขึ้นเป็นเส้นตรง — 6 จุดแวะ = 6×128 = 768 บิต แค่ส่วนหัวอย่างเดียว

04 · กลไกที่ 1

Micro-SID: บีบแต่ละจุดแวะให้เหลือแค่ 16 บิต

Micro-SID (uSID) แก้ปัญหา overhead ที่เพิ่งเห็นไปด้วยวิธีบีบอัด — แทนที่จะใช้ที่อยู่เต็ม 128 บิตต่อจุดแวะ 1 จุด ก็บีบแต่ละจุดแวะให้เหลือแค่ 16 บิต แล้วเอามาต่อกันในที่อยู่ 128 บิตเดียว แต่มีข้อควรระวังที่คนคำนวณผิดกันบ่อย: 128 บิตนั้นไม่ได้ว่างทั้งก้อน — ส่วนหน้าต้องกันไว้ให้ SID block (คำนำหน้าที่ใช้ร่วมกันทั้งโดเมน) ก่อนเสมอ ที่เหลือถึงจะเอามาซอยเป็นช่องละ 16 บิตได้

● แบบเดิม (1 จุดแวะ/128 บิต) ● Micro-SID (block 32 บิต + 6 ช่อง)

ที่อยู่ 128 บิตก้อนเดียวกัน ฝั่งซ้ายเก็บได้แค่ 1 จุดแวะเต็ม ๆ ฝั่งขวา (Micro-SID) กัน 32 บิตแรกไว้ให้ block เหลือ 96 บิต → 96 ÷ 16 = 6 ช่อง — overhead ที่เห็นไปก่อนหน้านี้หายไปเกือบหมด

จำนวนช่องไม่ใช่ค่าตายตัว

ตัวเลข 6 ช่องข้างบนมาจากการเลือก block ยาว 32 บิต (ค่าที่ใช้ในตัวอย่างและ config ที่ทดสอบจริงตลอดทั้งโพสต์นี้ — block 2001:bbbb::/32) ถ้า block ยาวขึ้นเป็น 48 บิต จะเหลือที่แค่ 80 บิต = 5 ช่อง — สูตรคือ (128 − block length) ÷ 16 เสมอ ไม่ใช่ 128 ÷ 16 อย่างที่มักเข้าใจกัน และถ้าเส้นทางยาวเกินจำนวนช่องที่มี ก็ต้องใส่ที่อยู่ก้อนถัดไปต่อใน SRH เพิ่ม

05 · พื้นฐานที่ 2

แต่ละช่อง 16 บิต เป็น GIB หรือ LIB — แยกด้วยช่วงตัวเลข ไม่ใช่แบ่งบิต

จาก Micro-SID ที่บีบทุกจุดแวะเหลือ 16 บิตเมื่อกี้ คำถามถัดมาคือ 16 บิตนั้นมีความหมายว่าอะไร? ข้อควรระวัง: มันไม่ใช่ "หนึ่งช่อง 16 บิต ถูกผ่าซอยครึ่งเป็นสองส่วนย่อย" — ทุกช่อง 16 บิตทั้งช่อง มีความหมายเดียวเต็ม ๆ ไม่ว่าจะเป็น "เราเตอร์ไหน" (GIB) หรือ "ทำอะไรที่นั่น" (LIB) โดยตัดสินจากค่าตัวเลขที่ใส่ในช่องนั้น ว่าตกอยู่ในช่วงไหนของทั้งหมด 0x0001–0xFFFF ที่ใช้ร่วมกันทุกช่อง — เราเตอร์ตัวหนึ่งจะมีช่อง un (GIB) ของตัวเองหนึ่งช่อง แล้วถ้ามันมีงานให้ทำ ก็จะมีอีกช่องแยกต่างหากถัดไปทันทีสำหรับค่า function (LIB)

ยิ่งลากค่า global-sid-entries ขึ้น ยิ่งเผื่อที่ให้ GIB มาก (รองรับเราเตอร์ได้เยอะขึ้น) แต่ LIB จะเหลือน้อยลง (ทำ service ต่อเราเตอร์ได้น้อยลง) และคลัง label ที่ต้องจองก็เล็กลงตาม LIB ไปด้วย

  • GIB (Global) ต้อง unique ทั้งเครือข่าย ห้ามซ้ำข้ามเราเตอร์ — เหมือนเลขทะเบียนที่ต้องไม่ซ้ำกันทั้งประเทศ
  • LIB (Local) unique แค่ภายในเราเตอร์ตัวเดียว เราเตอร์อื่นใช้เลขซ้ำกันได้สบาย — เหมือนเลขห้องภายในตึกที่ซ้ำกับตึกอื่นได้
  • ตัวเลขตัวเดียวที่ตั้งครั้งเดียว (เท่ากันทุกเราเตอร์ในเครือข่าย) กำหนดว่าเส้นแบ่งอยู่ตรงไหน
อย่าเข้าใจผิด: GIB กับ LIB ไม่ได้ซ้อนอยู่ในช่อง 16 บิตเดียวกัน

ตัวอย่างจริงจาก show command บนเราเตอร์ — un กับ function คนละช่อง 16 บิตกันเลย เรียงต่อกันในที่อยู่เดียวกัน ไม่ได้ซ้อนอยู่ในช่องเดียว:

2001:bbbb00064004::
● block — ใช้ร่วมกันทั้งเครือข่าย ● un = 6 (GIB) — เลขประจำเราเตอร์นี้ ● function = 16388 (LIB) — เลขงานที่ทำ

ค่า 6 กับ 16388 ใช้หน่วยตัวเลขเดียวกัน (6 อยู่โซน GIB, 16388 อยู่โซน LIB) แต่คนละช่องคนละตำแหน่ง — ที่มา: Nokia Segment Routing and PCE User Guide (ตัวอย่าง 2001:db8:00d1:d547::) และ show command จริงบนแล็บ

แล้วทำไมสองโซนนี้ห้ามทับกันเด็ดขาด

เหตุผลไม่ใช่แค่ระเบียบการจัดสรร แต่เป็นกลไกจริงในฮาร์ดแวร์ — เวลาเราเตอร์กินช่องของตัวเองเสร็จแล้วเลื่อนที่อยู่ไปทางซ้าย ค่าในช่องถัดไปจะขยับขึ้นมานั่งในตำแหน่งเดียวกับที่ค่า un เคยอยู่ พอดี แปลว่าตำแหน่งนั้นอาจมีค่า GIB หรือค่า LIB ก็ได้ เราเตอร์จึงต้องแยกให้ออกด้วยช่วงตัวเลขเพียงอย่างเดียว

คู่มือ Nokia ยืนยันเรื่องนี้ชัดในหัวข้อ microbinding SID: เวลา program FIB ระบบจะลง 2 รายการ คือ <block><uN><uB6>::/(block-length+32) และ <block><uB6>::/(block-length+16) — สังเกตรายการที่สอง: ค่า uB6 ซึ่งเป็นค่าโซน LIB ไปนั่งติดกับ block เลย คือตำแหน่งของ un พอดี รายการนี้จะปลอดภัยได้ก็ต่อเมื่อ GIB กับ LIB ไม่มีทางทับกันเท่านั้น ถ้าทับเมื่อไหร่ แพ็กเก็ตที่ตั้งใจจะวิ่งผ่านไปหาเราเตอร์ที่มี un ตรงกับเลขนั้น จะโดนเครื่องนี้ดักกินเป็น function ของตัวเองทันที

06 · ลงลึกอีกนิด

ตัวเลขเราเตอร์ (GIB) ตั้งยังไง แล้วพลาดได้ตรงไหน

รู้แล้วว่า GIB คือส่วนที่บอกว่า "เราเตอร์ไหน" — คำถามต่อมาคือ แล้วเราเตอร์แต่ละตัวได้เลขประจำตัวของตัวเองมาจากไหน? ค่านี้ถูกตั้งด้วยคำสั่งที่ชื่อ un (ย่อจาก uSID Node) — ตัวอย่างจริงจากเอกสาร: เราเตอร์หนึ่งตั้ง un value 1 อีกตัวตั้ง un value 1281 ทั้งสองค่าต้องอยู่ในโซน GIB เท่านั้น (ห้ามหลุดไปโซน LIB) และห้ามซ้ำกับเราเตอร์ตัวอื่นในเครือข่ายเดียวกันเด็ดขาด

● ตั้งถูก — ตกอยู่ในโซน GIB ● ตั้งพลาด — หลุดไปโซน LIB

ช่วงตัวเลขที่ระบบยอมให้พิมพ์ในคำสั่ง un value คือ 1 ถึง 1,048,575 เสมอ — ไม่ว่าจะตั้ง GIB ไว้ใหญ่แค่ไหนก็ตาม ระบบไม่เช็คให้ว่าเลขที่พิมพ์ไปนั้นยังอยู่ในโซน GIB จริงหรือเปล่า

จุดพลาดจริงที่เกิดได้

สมมติตั้ง GIB ไว้แค่ 1–16,383 (ค่าเริ่มต้น) แต่ดันพิมพ์ un value 20000 ไป — ระบบจะรับค่านั้นทันที ไม่มี error ไม่มี warning ทั้งที่ 20,000 มันไปตกอยู่ในโซน LIB แทน ซึ่งเป็นพื้นที่ที่กันไว้ให้ service function ของเราเตอร์ตัวอื่นใช้ กลายเป็นเลขไปชนกับพื้นที่ที่ไม่ควรชนโดยไม่มีใครรู้ตัว

  • กฎที่ต้องเช็คเองทุกครั้ง: un value ต้องน้อยกว่า global-sid-entries × 1024 เสมอ
  • ไม่มีเครื่องมือใน CLI ที่คอยเตือนเรื่องนี้ให้ — เป็นการบ้านที่ต้องคำนวณเองล้วน ๆ

07 · เห็นภาพรวม

เดินตามแพ็กเก็ตทีละ hop จริง ๆ

เอาทุกอย่างที่ผ่านมารวมกัน — สมมติลูกค้าที่ CE1 ส่งแพ็กเก็ต IPv6 ธรรมดาไปถึงบริการหนึ่งที่อยู่หลัง R3 (CE1 ไม่รู้จัก SRv6 เลย) เส้นทางจริงต้องผ่าน R1 → R2 → R3 พอถึง R1 ซึ่งทำหน้าที่ PE1 (ingress) จึงเริ่ม encapsulate ด้วยที่อยู่ปลายทางแบบ Micro-SID — เอาช่อง 16 บิตมาเรียงต่อกัน โดยใช้ block เดียวกับที่ทดสอบจริงในข้อ 11 (2001:bbbb) แล้วตามด้วยค่า un ของ R1, R2, R3 (ค่าโซน GIB ทั้งสามช่อง — 1, 2, 3 ตามสูตร) แล้วปิดท้ายด้วยค่า function ของบริการที่ R3 (ค่าโซน LIB — 4004 จาก udt46 value 5 ตัวจริงที่วัดมา) จากนั้นทุก hop จะดูช่องหน้าสุดช่องเดียวเสมอ แล้วเลื่อนช่องที่กินแล้วทิ้งไป กดปุ่มด้านล่างเพื่อเดินทีละขั้นเอง จะได้อ่านรายละเอียดทันทุกจุด

08 · จุดที่มักงง

ก็บอกไม่มี MPLS แล้ว ทำไมยังเห็นคำว่า label

เดินตามแพ็กเก็ตทีละ hop ไปเมื่อกี้ จะเห็นว่าตลอดทางไม่มีคำว่า label โผล่มาเลยสักครั้ง แต่พอเปิดคอนฟิกจริงบน Nokia SR OS กลับเจอคำว่า label เต็มไปหมด — คำตอบสั้น ๆ คือ บนสายสัญญาณจริง ไม่มี MPLS label ปนอยู่เลยแม้แต่นิดเดียว แพ็กเก็ตที่วิ่งระหว่างเราเตอร์เป็น IPv6 + SRH ล้วน ๆ ตลอดเส้นทาง — แต่ ภายในตัวเราเตอร์บางรุ่น (ที่ใช้ชิปประมวลผลรุ่นที่มีอยู่แล้วสำหรับ MPLS) ระบบเลือกใช้กลไก lookup table แบบเดียวกับที่ MPLS ใช้อยู่แล้ว มาช่วยค้นหาว่า "เลข LIB นี้ต้องทำอะไร" ให้เร็วขึ้น ซึ่งกลไกนั้นต้องการ "เลข label" เป็นดัชนีค้นหาภายในตัวมันเอง

● บนสาย = IPv6 ล้วน ไม่มี label ● ภายในกล่อง = แปลงเป็น label ชั่วคราว

แพ็กเก็ตที่ออกจากเราเตอร์ยังเป็น IPv6 ล้วนเหมือนเดิมทุกประการ — label เกิดขึ้นแค่ชั่วขณะที่อยู่ในหน่วยประมวลผลภายในกล่องเดียวเท่านั้น ไม่เคยถูกส่งออกไปข้างนอก

สรุปให้จำง่าย

09 · กลไกที่ 2

Reserved Label Block: ไม่ต้องตรงเลข hex ของ LIB แต่ต้องพอใช้งานจริง

label ภายในกล่องที่เพิ่งเห็นไป ถูกจับคู่แบบ 1 ต่อ 1 กับทุกค่า LIB ที่ถูกใช้งานจริง ระบบเลยต้องมี "คลัง label" (Reserved Label Block) กันไว้ให้พอ — และนี่คือจุดที่คนตั้งค่าใหม่ ๆ มักเข้าใจผิด: คิดว่าตัวเลขในคลัง label ต้องตรงกับค่า hex ของ LIB ด้วย ซึ่งไม่จำเป็นเลย

● LIB (พื้นที่ function จริงในที่อยู่ IPv6) ● คลัง Label ที่จอง (ตัวเลข MPLS label คนละพื้นที่กันเลย)

สองแท่งนี้ยาวเท่ากันเป๊ะ (จำนวน entries เท่ากัน) แต่อยู่คนละช่วงตัวเลขกันโดยสิ้นเชิง — LIB เป็นเลข hex ในที่อยู่ IPv6 (เช่น E000-FFFF) ส่วน label pool เป็นเลข MPLS label ธรรมดา (เช่น 30000-38191) ระบบจับคู่ให้เองภายใน ไม่ต้องให้ตัวเลขตรงกัน

แล้วทำไม GIB ไม่ต้องมีคลัง label บ้าง

GIB บอกแค่ "เราเตอร์ไหน" — งานของเราเตอร์ตอนเช็คส่วนนี้ คือดูว่า GIB ในแพ็กเก็ตตรงกับค่า un ของตัวเองหรือเปล่า เหมือนเช็คว่าจดหมายส่งถึงบ้านเลขที่ตัวเองไหม ซึ่งเป็นการจับคู่กับ prefix เดียว ที่ตัวเองประกาศออกไปทาง IGP ตามปกติอยู่แล้ว (เหมือน route lookup ทั่วไป) ไม่จำเป็นต้องมีตาราง lookup แยกไว้ล่วงหน้าสำหรับทุกค่า GIB ที่เป็นไปได้ในเครือข่าย เพราะเราเตอร์แต่ละตัวสนใจแค่ค่าของตัวเองค่าเดียว — จึงไม่ต้องมีคลัง label มารองรับส่วนนี้เลย

LIB ต่างออกไปโดยสิ้นเชิง — ค่า LIB แต่ละค่า "ภายในเราเตอร์ตัวเดียวกัน" หมายถึงงานคนละอย่างกัน (คนละ service, คนละปลายทาง, คนละ policy) เมื่อแพ็กเก็ตมาถึงเราเตอร์ที่ถูกต้องแล้ว (GIB ตรงแล้ว) เราเตอร์ต้องแยกแยะต่อว่า LIB ค่านี้หมายถึงงานไหนในบรรดาหลายสิบหลายพันงานที่มีอยู่ ระบบจึงต้องกันที่ในคลัง label ไว้ให้พอกับจำนวน function ที่จะใช้งานจริง (ทั้ง static และ dynamic) ไม่ใช่ค่าที่ใช้อยู่ตอนนี้เท่านั้น

กฎที่ต้องจำ — LIB คือ "เพดาน" ไม่ใช่ "พื้น"

คู่มือ Nokia เขียนไว้ตรงข้ามกับที่มักเข้าใจกัน: ขนาด LIB (2^16 − global-sid-entries × 1024) คือเพดานสูงสุดตามทฤษฎี ไม่ใช่ขนาดที่ต้อง reserve ให้ครบเสมอไป — "a label-block should not need exceed that value" (จองเกินกว่านั้นก็แค่เปลือง label เปล่า ๆ) ขนาดที่ถูกต้องจริง ๆ มี 3 ชั้น: (1) พื้นแข็ง ต้อง ≥ static-function max-entries เสมอ (CLI reject ทันทีถ้าไม่ถึง), (2) พื้นใช้งานจริง ควร ≥ max-entries บวกจำนวน dynamic function ที่คาดว่าจะเกิดขึ้นจริง (ไม่มี CLI เช็คให้ — พลาดแล้วเงียบตามที่คุยในข้อ 13), (3) เพดาน ไม่ควรเกินขนาด LIB เต็ม เพราะเกินไปก็แค่เสีย label เปล่า ๆ ไม่ได้ผิดกฎอะไร

ตัวเลขที่ต้องตรงกันแน่ ๆ มีแค่อย่างเดียวคือ "จำนวน" (count) ระหว่างคลัง label กับจำนวน function ที่ใช้จริง — เริ่มที่เลขอะไรก็ได้ ขอแค่ไม่ไปชนกับ label range อื่นที่ใช้อยู่ในเครื่องเดียวกัน

10 · กลไกที่ 3

static-function: ผ่า LIB อีกชั้นเป็นโซน static กับ dynamic

ภายใน LIB เดียวกัน (ที่คลัง label ก้อนเดียวครอบคลุมอยู่แล้วตามข้อที่แล้ว) ยังถูกผ่าอีกชั้นด้วยค่า static-function max-entries: ตั้งแต่ต้น LIB ไปจนถึง max-entries คือโซน static — operator พิมพ์ค่าฟังก์ชันเองตรง ๆ ได้ค่าเดิมทุกครั้งแม้ reboot ส่วนที่เหลือทั้งหมดคือโซน dynamic — ระบบเลือกช่องว่างให้เองอัตโนมัติ ไม่การันตีว่าจะได้เลขเดิมทุกครั้ง

  • สิ่งที่ต้องเป็น static เสมอ เพราะมีคนอื่นอ้างอิงค่าตรง ๆ จึงต้องคาดเดาได้แน่นอน: uA (adjacency ที่กำหนดเอง), service micro-SID (uDT4/uDT6/uDT46/uDX2/uDX6 ที่ระบุ function value เอง), และ binding-SID (uB6) ของ SRv6 policy — ทั้งสามชนิดแย่งที่กันในโซน static เดียวกัน ไม่ใช่คนละโควตาแยกกัน
  • un (GIB) ไม่เกี่ยวข้องกับโซนนี้เลย เพราะอยู่คนละ pool ตั้งแต่ต้น ไม่กินโควตา static-function แม้แต่ช่องเดียว
  • โซน dynamic เริ่มที่ LIB start + max-entries พอดี (ไม่ใช่ +max-entries+1) — วัดจากแล็บ: ตั้ง max-entries 16 แล้ว uDT46 ตัวแรกที่ระบบจัดให้เองได้ 0x4010 (16400) แปลว่าโซน static คือ index 1–16 = 0x4000–0x400F เป๊ะ

Oper Func = (global-sid-entries × 1024) + (ค่าที่พิมพ์ − 1)

สังเกตว่ามี −1 อยู่ด้วย — ua 1 ให้ค่าจริงเท่ากับจุดเริ่มต้นของ LIB พอดี ไม่ใช่จุดเริ่ม+1 ทดสอบบน 7750 SR-1 จริง: ตั้ง global-sid-entries 16 (LIB เริ่ม 0x4000) แล้วสั่ง ua 1 / ua 2 / ua 3 ได้ SID ลงท้าย 4000:: / 4001:: / 4002:: (Oper Func = 16384 / 16385 / 16386)

จากนั้นเปลี่ยนแค่ global-sid-entries เป็น 56 (LIB เริ่ม 0xE000) โดยไม่แตะคอนฟิก uA เลยสักบรรทัด — ค่าทั้งชุดขยับตามทันทีเป็น e000:: / e001:: / e002:: (57344 / 57345 / 57346) ยืนยันว่าเลขที่พิมพ์เป็น index ที่ผูกกับตำแหน่งเริ่มของ LIB จริง ไม่ใช่ค่าตายตัว

ยืนยันด้วย service SID ทุกชนิด ไม่ใช่แค่ uA: ทดสอบ udt46 value 5, udx2 value 6, udt4 value 7, udt6 value 8, udt2u value 9, udt2m value 10 บนบล็อกเดียวกัน (LIB เริ่ม 0x4000) ได้ SID ลงท้าย 4004:: / 4005:: / 4006:: / 4007:: / 4008:: / 4009:: ตามลำดับ — สูตรเดียวกันเป๊ะ ไม่มี offset แยกตามชนิด function และ Nokia เอง ก็มีตัวอย่างในคู่มือ Advanced Configuration Guide ที่ใช้ udx2 value 5 แล้วได้ 4004:: (16388) ตรงกับสูตรนี้พอดี

ข้อควรรู้เพิ่ม: index ที่พิมพ์ (เช่น value 5) ใช้ "พูลเดียวกันทั้ง block" — ชนกันได้ข้ามชนิด function, ข้าม uA, และข้ามทุก locator ที่ใช้ block เดียวกัน แม้ SID สุดท้ายจะไม่ชนกันบนสาย (คนละ un) ระบบก็ยัง reject ให้ เพราะเช็คที่ระดับ block ไม่ใช่ระดับ locator — ต้องวางแผน index ให้ไม่ชนกันทั้งเครือข่ายที่แชร์ block เดียวกัน

binding-SID (uB6) ใส่แค่ค่าเดียวลอย ๆ ไม่ได้

SRv6 policy binding-SID ที่ head-end รับ ต้องมาในรูปเต็ม <block><uN><uB6> เท่านั้น — ต้องมี uN ของเราเตอร์เจ้าของนำหน้าเสมอ จะส่งแค่ค่า uB6 ช่องเดียวแบบลอย ๆ ไม่ได้ ตรงกับกลไก 2 FIB entry ในข้อ 05 (entry สั้นที่ไม่มี uN ใช้ได้แค่ตอนแพ็กเก็ตเลื่อนมาถึงตำแหน่งนั้นแล้วเท่านั้น ไม่ใช่ที่อยู่ที่ route ได้จากภายนอกโดยตรง)

ข้อควรระวังจริง: แก้ max-entries ทีหลัง = service สะดุดทั้ง block

ค่าเริ่มต้นของ max-entries คือ 1 — ถ้าจะใช้ static function มากกว่า 1 ตัว ต้องปรับเพิ่มเอง และที่สำคัญกว่านั้น: การแก้ค่า max-entries ทีหลังจะสลับ admin-state ของ block ทั้งก้อนโดยอัตโนมัติ ตาม CLI warning ของจริง แปลว่า service ทุกตัวที่ผูกกับ block นั้นจะสะดุดชั่วขณะทันที — ต้องวางแผนจำนวน static function ที่ต้องใช้ให้ครบตั้งแต่วันแรก ไม่ใช่ค่อยขยายทีหลัง

12 · ตัวอย่างตัวเลขจริง

ลองคำนวณดูจริง ๆ

รวมทุกกลไกที่ผ่านมาเข้าด้วยกัน จะเห็นว่ามีตัวเลขตัวเดียวที่ต้องเลือก แล้วทุกอย่างคำนวณตามมาหมด — เอาค่านั้นคูณ 1024 จะได้จุดตัดระหว่าง GIB กับ LIB ยิ่งเลือกมาก ยิ่งเผื่อที่ให้ GIB (รองรับเราเตอร์เยอะ) แต่ LIB (และคลัง label ที่ต้องจอง) จะเล็กลงตาม

ค่าที่เลือกจุดตัด (×1024)GIB ≈ รองรับกี่เราเตอร์LIB ≈ ต้องจอง label กี่ช่อง
16 (ค่าเริ่มต้น) 0x4000 16,383 ตัว 49,152 ช่อง
56 0xE000 57,343 ตัว 8,192 ช่อง
60 (สูงสุด) 0xF000 61,439 ตัว 4,096 ช่อง

เห็น trade-off ชัดเจน: เลือก 60 รองรับเราเตอร์ได้เยอะสุด แต่เหลือที่ให้ทำ function ต่อเราเตอร์แค่ 4,096 ช่อง — ต้องเลือกให้เหมาะกับขนาดเครือข่ายจริง ไม่ใช่เลือกสูงสุดไว้ก่อนเสมอไป

13 · ข้อควรระวัง

จองน้อยไป — ส่วนใหญ่ระบบเตือน มีจุดเดียวที่เงียบ

เห็น trade-off ของการเลือกตัวเลขไปแล้ว ทีนี้มาดูว่าถ้าคำนวณคลัง label ผิดจริง ๆ จะเกิดอะไรขึ้น — ผลทดสอบจริงบน SR-SIM พลิกความเข้าใจเดิม: การละเมิดขอบเขต static ถูก reject ตอน commit ทันที ถึง 3 ใน 4 กรณี มีแค่กรณีเดียวเท่านั้นที่เงียบจริง

  • ลด max-entries ต่ำกว่าจำนวน static function ที่ใช้อยู่ → reject ทันที: MINOR: MGMT_CORE #4001: ... Cannot configure function value as it is exceeding max entries
  • ตั้ง static index เกิน max-entries (เช่น ua 17 ตอน max-entries 16) → reject ด้วย error เดียวกัน
  • ย่อ label-block ให้เล็กกว่า max-entries → reject ทันที: MINOR: MGMT_CORE #4001: ... Start and end labels range 2 must be more than max-entries
จุดเดียวที่เงียบจริง: โซน dynamic หมด

ถ้า reserved-label-block เหลือที่ไม่พอสำหรับ dynamic function ตัวถัดไป (เช่น static ใช้ไป 16 ช่องตาม max-entries แล้ว label-block มีแค่ 17 ช่อง เหลือ dynamic แค่ 1 ช่องซึ่งถูกใช้ไปแล้ว) แล้วสร้าง service ใหม่ที่ต้องการ function แบบ dynamic อีกตัว — commit ผ่านปกติ ไม่มี error, service ขึ้น Admin/Oper State: Up หลอกตาเต็มที่ แต่ไม่มี SID เกิดขึ้นจริงเลย VPN นั้น blackhole เงียบ ๆ หลักฐานเดียวที่มีคือ log ระดับ MINOR:

MINOR: SVCMGR #2135 Base "Allocation of function failed for vprn 200 srv6-instance 1 micro-segment-locator uSID-Alg0-Loc function udt46 value 0."

อีกจุดที่อันตราย: แก้ max-entries หรือขนาด label-block ทีหลัง = dynamic SID เลื่อนเงียบ ๆ

ทดสอบจริง: service ที่ใช้ function แบบ dynamic (ไม่ระบุ value เอง) ได้ SID 2001:bbbb:1:4010:: (16400) อยู่ดี ๆ — พอแก้ max-entries จาก 16 เป็น 20 (มี service รันอยู่แล้ว) แล้ว commit: SID ของ service เดิมขยับเป็น 4014:: (16404) ทันที โดยไม่มี error, ไม่มี service flap แจ้งเตือน มีแค่ log ทั่วไป "Commit ... succeeded" เท่านั้น — ทำแบบเดียวกันกับการย่อ/ขยาย reserved-label-block ก็เจอ SID เลื่อนซ้ำอีกทุกครั้งที่แตะ

ของที่ตั้ง static value เองไว้ (เช่น udt46 value 5) ไม่เคยขยับเลยแม้แต่ครั้งเดียว ต่อให้แก้ max-entries หรือ resize label-block กี่รอบก็ตาม — เพราะ CLI ไม่มีทาง reallocate ค่าที่ operator กำหนดเองตายตัวอยู่แล้ว มีแต่ dynamic เท่านั้นที่ระบบไปแตะได้

ผลกระทบจริง: BGP re-advertise SID ใหม่ให้ทันที และ route ในตาราง VRF ของอีกฝั่งชี้ไปที่ SID ใหม่ — แปลว่าการแก้ max-entries หรือขนาด label-block บนเครื่องที่มี service ใช้งานอยู่ คือ service-affecting change แม้ CLI จะ commit ผ่านแบบเงียบ ๆ ก็ตาม ต้องขอ maintenance window เหมือนงานที่กระทบ service จริง ไม่ใช่แค่ config เปลี่ยนเฉย ๆ (ทดสอบบน SR-SIM 26.3.R1 — พฤติกรรมนี้เป็น logic ฝั่ง control plane จึงน่าจะตรงกับฮาร์ดแวร์จริง แต่ยังไม่ได้ยืนยันบนเครื่องจริง)

บทเรียน

show router mpls-labels label-range ไม่มีคอลัมน์ used/available สำหรับ reserved-label-block เลย (มีแค่ Name/Start/End/Total) จึงไม่มีทางรู้ล่วงหน้าว่าใกล้เต็มหรือยังจากคำสั่ง show ปกติ — วิธีเดียวที่จะจับกรณีนี้ได้บน production คือตั้ง monitor บน log event SVCMGR #2135 ไว้เตือนล่วงหน้า ควบคู่กับ (1) กำหนด value แบบ static ให้ service ที่แคร์ความนิ่งของ SID เสมอ และ (2) วางแผนขนาด max-entries/label-block ให้ครบตั้งแต่วันแรก เพราะการมาขยายทีหลังจะทำให้ dynamic SID ทุกตัวเลื่อนตาม

14 · สรุป

รวมทุกอย่างเข้าด้วยกัน

  • Segment Routing ฝัง "รายการจุดแวะ" ไปกับแพ็กเก็ตตั้งแต่ต้นทาง ไม่ต้องเดาทางทีละ hop
  • SRv6 เอาที่อยู่ IPv6 มาเป็นจุดแวะโดยตรง ไม่มี MPLS label ปนบนสายเลย
  • Micro-SID บีบแต่ละจุดแวะเหลือ 16 บิต ใส่ได้หลายจุดในที่อยู่เดียว (จำนวนขึ้นกับ SID block length เช่น block 32 บิต ใส่ได้ 6 จุด) แก้ปัญหา overhead
  • ทุกช่อง 16 บิตเป็นได้ทั้ง GIB (ระบุเราเตอร์) หรือ LIB (ระบุ function) — แยกกันด้วยช่วงตัวเลข ไม่ใช่แบ่งบิตภายในช่องเดียว
  • ค่าเราเตอร์ (un) ต้องเลือกเองให้อยู่ในโซน GIB เสมอ — CLI ยอมรับตัวเลขกว้างกว่านั้นมาก และไม่เตือนถ้าเผลอหลุดไปโซน LIB
  • label ที่เห็นในคอนฟิกเป็นแค่กลไก lookup ภายในฮาร์ดแวร์บางรุ่น ไม่เคยออกไปบนสายจริง
  • GIB ไม่ต้องมีคลัง label เพราะแค่จับคู่กับ prefix เดียวของตัวเองผ่าน IGP ตามปกติ แต่ LIB ต้องมี เพราะแต่ละค่าคืองานคนละอย่างที่ต้องแยกแยะแบบ index ต่อค่า
  • คลัง label ต้องมี จำนวน ครบเท่า LIB เสมอ แต่ ตัวเลขไม่ต้องตรงกับ hex ของ LIB — ละเมิดขอบเขต static ส่วนใหญ่ reject ทันทีตอน commit แต่ถ้าโซน dynamic หมดพอดี จะเงียบจริง (commit ผ่าน, service ขึ้น Up หลอกตา, ไม่มี SID) ต้องคำนวณให้ครบตั้งแต่แรกและ monitor log SVCMGR #2135 ไว้
  • static-function ผ่า LIB อีกชั้นเป็นโซน static (uA/service-SID/binding-SID ที่ตั้งเอง) กับ dynamic (ระบบเลือกให้) — ค่าที่พิมพ์เป็น index ไม่ใช่ hex ของ LIB ตรง ๆ (สูตรจริง: LIB start + index − 1) และแก้ max-entries ทีหลังจะทำให้ block ทั้งก้อน admin-state toggle
  • binding-SID (uB6) ของ SRv6 policy ต้องอ้างอิงแบบเต็มรูป <block><uN><uB6> เสมอ ใส่แค่ค่า uB6 ลอย ๆ ไม่ได้
