Nokia SR OS กับ
SRv6 Micro-SID

SRv6 ถูกพูดถึงว่าไม่ต้องพึ่ง MPLS อีกต่อไป — ที่อยู่ปลายทางแบบ IPv6 บอกทุกอย่างที่ต้องรู้ในตัวเองอยู่แล้ว แต่พอไปเปิดคอนฟิกจริงบน Nokia SR OS ของฟีเจอร์ที่ชื่อ Micro-SID กลับเจอคำว่า mpls-labels, reserved-label-block โผล่มาเต็มไปหมด หน้านี้จะพาไปดูตั้งแต่พื้นฐานว่าทำไมถึงเป็นแบบนั้น ไปจนถึงลองลากเลื่อนดูการแบ่ง GIB/LIB เองและดูแพ็กเก็ตเดินทางทีละ hop จริง — เริ่มจากศูนย์ ไม่ต้องมีพื้นฐาน SRv6 มาก่อน

เลื่อนลงเพื่อเริ่มเรียนรู้
01 · จุดเริ่มต้น

Segment Routing คืออะไร (ไม่ต้องรู้ MPLS มาก่อน)

เครือข่ายแบบเดิม แต่ละราวเตอร์ต้อง "เดาทาง" เองทีละ hop — เหมือนถามทางที่สี่แยกไปเรื่อย ๆ จนถึงปลายทาง Segment Routing เปลี่ยนวิธีคิดใหม่: ให้ราวเตอร์ต้นทางเขียน "รายการจุดแวะ" ทั้งหมดแนบไปกับแพ็กเก็ตตั้งแต่แรก แต่ละราวเตอร์ระหว่างทางแค่เปิดดูจุดแวะถัดไปในรายการแล้วส่งต่อ ไม่ต้องเดาเองเลย

01

ต้นทางตัดสินใจ

ราวเตอร์ต้นทางเลือกเส้นทางทั้งหมดล่วงหน้า ไม่ปล่อยให้แต่ละจุดตัดสินใจเอง

02

รายการฝังไปกับแพ็กเก็ต

"จุดแวะ" (segment) ทุกจุดถูกเขียนแนบไปกับแพ็กเก็ตเอง ไม่ต้องมีใครจำเส้นทางไว้ล่วงหน้า

03

แต่ละจุดทำตามคิวถัดไป

ราวเตอร์ระหว่างทางแค่มองจุดแวะถัดไปในรายการ ทำตามแล้วส่งต่อ ไม่ต้องคิดอะไรเพิ่ม

02 · พื้นฐานที่ 1

SRv6 เอา "จุดแวะ" ไปฝังไว้ในที่อยู่ IPv6 เลย

จากแนวคิด "ฝังรายการจุดแวะไปกับแพ็กเก็ต" ในข้อที่แล้ว คำถามต่อมาคือ — แต่ละจุดแวะจะเก็บด้วยอะไร? SRv6 (Segment Routing over IPv6) เลือกวิธีที่ตรงไปตรงมาที่สุด: ให้ จุดแวะแต่ละจุดคือที่อยู่ IPv6 หนึ่งตัวเลย ไม่ต้องมีเลข label แยกต่างหากแบบ MPLS รายการจุดแวะทั้งหมดถูกเก็บไว้ใน header พิเศษท้ายแพ็กเก็ตที่เรียกว่า SRH (Segment Routing Header) และที่อยู่ IPv6 แต่ละตัวยังแบ่งเป็น 2 ส่วนในตัวมันเอง: Locator (ราวเตอร์ไหน) และ Function (ทำอะไรที่นั่น)

● Locator (ราวเตอร์ไหน) ● Function (ทำอะไร)

แพ็กเก็ตพกรายการจุดแวะ (สี่เหลี่ยมเล็ก ๆ ด้านบน) ไปด้วย ทุกครั้งที่ผ่านราวเตอร์หนึ่งตัว จุดแวะที่ทำเสร็จแล้วจะถูกตัดออกจากรายการ — ที่อยู่ปลายทางปัจจุบันก็จะเปลี่ยนเป็นจุดแวะถัดไปโดยอัตโนมัติ

03 · ปัญหาที่ตามมา

ยิ่งเส้นทางซับซ้อน ยิ่งต้องแบกรายการยาว

วิธีของ SRv6 ในข้อที่แล้วเรียบง่ายดี แต่แลกมาด้วยต้นทุนที่มองข้ามไม่ได้: ที่อยู่ IPv6 หนึ่งตัวยาวถึง 128 บิต ถ้าเส้นทางหนึ่งต้องผ่าน 6 จุดแวะ ก็ต้องแนบที่อยู่ 6 ตัวเต็ม ๆ ไปกับทุกแพ็กเก็ต — ยิ่งเครือข่ายใหญ่ ยิ่งทำ traffic engineering ซับซ้อน รายการนี้ก็ยิ่งยาว กินพื้นที่และแรงประมวลผลทุก hop

● ขนาด SRH ที่ต้องแบก

ยิ่งจำนวนจุดแวะเพิ่ม แท่งกราฟ (ขนาด header ที่ต้องแบก) ก็ยิ่งยาวขึ้นเป็นเส้นตรง — 6 จุดแวะ = 6×128 = 768 บิต แค่ส่วนหัวอย่างเดียว

04 · กลไกที่ 1

Micro-SID: บีบแต่ละจุดแวะให้เหลือแค่ 16 บิต

Micro-SID (uSID) แก้ปัญหา overhead ที่เพิ่งเห็นไปด้วยวิธีบีบอัด — แทนที่จะใช้ที่อยู่เต็ม 128 บิตต่อจุดแวะ 1 จุด ก็บีบแต่ละจุดแวะให้เหลือแค่ 16 บิต เมื่อเล็กขนาดนี้ ก็เอาหลาย ๆ จุดแวะมาต่อกันในที่อยู่ 128 บิตเดียวได้เลย — 128 ÷ 16 = ใส่ได้ถึง 8 จุดแวะ ในพื้นที่ที่แต่ก่อนใส่ได้แค่ 1 จุด

● แบบเดิม (1 จุดแวะ/128 บิต) ● Micro-SID (สูงสุด 8 จุดแวะ/128 บิต)

ที่อยู่ 128 บิตก้อนเดียวกัน ฝั่งซ้ายเก็บได้แค่ 1 จุดแวะเต็ม ๆ ฝั่งขวา (Micro-SID) แบ่งเป็น 8 ช่องเล็ก เก็บได้ถึง 8 จุดแวะ — ปัญหา overhead ที่เห็นไปก่อนหน้านี้หายไปเกือบหมด

05 · พื้นฐานที่ 2

16 บิตนั้น แบ่งเป็น 2 ส่วน: GIB กับ LIB

จาก Micro-SID ที่บีบทุกจุดแวะเหลือ 16 บิตในข้อที่แล้ว คำถามถัดมาคือ 16 บิตนั้นเก็บอะไรบ้าง? ลองนึกถึง เบอร์โทรศัพท์: รหัสพื้นที่ + เลขในสาย — พื้นที่ 16 บิตของ Micro-SID ก็ถูกตัดแบ่งแบบเดียวกัน ด้วยตัวเลขตัวเดียวที่ตั้งครั้งเดียวทั้งเครือข่าย

● GIB — รหัสพื้นที่ (ราวเตอร์ไหน) ● LIB — เลขในสาย (ทำอะไรในราวเตอร์นั้น)
16

ยิ่งลากค่า global-sid-entries ขึ้น ยิ่งเผื่อที่ให้ GIB มาก (รองรับราวเตอร์ได้เยอะขึ้น) แต่ LIB จะเหลือน้อยลง (ทำ service ต่อราวเตอร์ได้น้อยลง) และคลัง label ที่ต้องจองก็เล็กลงตาม LIB ไปด้วย

  • GIB (Global) ต้อง unique ทั้งเครือข่าย ห้ามซ้ำข้ามราวเตอร์ — เหมือนรหัสพื้นที่ที่บอกว่าเบอร์นี้อยู่จังหวัดไหน
  • LIB (Local) unique แค่ภายในราวเตอร์ตัวเดียว ราวเตอร์อื่นใช้เลขซ้ำกันได้สบาย — เหมือนเลขต่อภายในออฟฟิศที่ซ้ำกับออฟฟิศอื่นได้
  • ตัวเลขตัวเดียวที่ตั้งครั้งเดียว (เท่ากันทุกราวเตอร์ในเครือข่าย) กำหนดว่าเส้นแบ่งอยู่ตรงไหน
06 · ลงลึกอีกนิด

ตัวเลขราวเตอร์ (GIB) ตั้งยังไง แล้วพลาดได้ตรงไหน

รู้แล้วว่า GIB คือส่วนที่บอกว่า "ราวเตอร์ไหน" — คำถามต่อมาคือ แล้วราวเตอร์แต่ละตัวได้ค่า GIB ของตัวเองมาจากไหน? ค่า "รหัสพื้นที่" ของราวเตอร์แต่ละตัวถูกตั้งด้วยคำสั่งที่ชื่อ un (ย่อจาก uSID Node) — ตัวอย่างจริงจากเอกสาร: ราวเตอร์หนึ่งตั้ง un value 1 อีกตัวตั้ง un value 1281 ทั้งสองค่าต้องอยู่ในโซน GIB เท่านั้น (ห้ามหลุดไปโซน LIB) และห้ามซ้ำกับราวเตอร์ตัวอื่นในเครือข่ายเดียวกันเด็ดขาด

● ตั้งถูก — ตกอยู่ในโซน GIB ● ตั้งพลาด — หลุดไปโซน LIB

ช่วงตัวเลขที่ระบบยอมให้พิมพ์ในคำสั่ง un value คือ 1 ถึง 1,048,575 เสมอ — ไม่ว่าจะตั้ง GIB ไว้ใหญ่แค่ไหนก็ตาม ระบบไม่เช็คให้ว่าเลขที่พิมพ์ไปนั้นยังอยู่ในโซน GIB จริงหรือเปล่า

จุดพลาดจริงที่เกิดได้

สมมติตั้ง GIB ไว้แค่ 1–16,383 (ค่าเริ่มต้น) แต่ดันพิมพ์ un value 20000 ไป — ระบบจะรับค่านั้นทันที ไม่มี error ไม่มี warning ทั้งที่ 20,000 มันไปตกอยู่ในโซน LIB แทน ซึ่งเป็นพื้นที่ที่กันไว้ให้ service function ของราวเตอร์ตัวอื่นใช้ กลายเป็นเลขไปชนกับพื้นที่ที่ไม่ควรชนโดยไม่มีใครรู้ตัว

  • กฎที่ต้องเช็คเองทุกครั้ง: un value ต้องน้อยกว่า global-sid-entries × 1024 เสมอ
  • ไม่มีเครื่องมือใน CLI ที่คอยเตือนเรื่องนี้ให้ — เป็นการบ้านที่ต้องคำนวณเองล้วน ๆ

ลองดูตัวอย่างหลาย ๆ แบบเทียบกัน จะเห็นภาพชัดขึ้นว่าเส้นแบ่งอยู่ตรงไหนกันแน่:

07 · เห็นภาพรวม

เดินตามแพ็กเก็ตทีละ hop จริง ๆ

เอาทุกอย่างที่ผ่านมารวมกัน — สมมติลูกค้าที่ CE1 ต้องส่งข้อมูลไปถึงบริการหนึ่งที่อยู่หลัง R3 เส้นทางจริงต้องผ่าน R1 → R2 → R3 ที่อยู่ปลายทางที่ราวเตอร์ต้นทางประกอบไว้ให้จึงเป็นการเอา 3 "ช่อง" มาต่อกันเรียงตามลำดับที่ต้องผ่าน — แต่ละช่องคือ GIB (ราวเตอร์ไหน) บวก LIB (ทำอะไรที่นั่น) รวมกัน

● GIB ตรงกับ un ของราวเตอร์นั้น ● LIB บอกว่าต้องทำอะไร

ทุกราวเตอร์ตรวจช่องที่ "อยู่หน้าสุด" ของที่อยู่ปลายทางเสมอ — ถ้า GIB ตรงกับ un ของตัวเอง ก็รู้ว่าถึงคิวตัวเองแล้ว จากนั้นดู LIB ว่าต้องทำอะไร ก่อนเผยช่องถัดไปให้เป็นที่อยู่ปลายทางใหม่ แล้วส่งต่อ

  • GIB ตรงกับ un ตัวเอง → ราวเตอร์รู้ทันทีว่านี่คือคิวของตัวเอง ไม่ใช่ของคนอื่น
  • LIB = 0 → ไม่มีคำสั่งพิเศษ แค่ส่งต่อไปช่องถัดไปเฉย ๆ (R1, R2 ในตัวอย่างนี้)
  • LIB ≠ 0 → มีคำสั่งเฉพาะให้ทำที่ราวเตอร์นี้ เช่น ถอดรหัสส่งเข้า VPN แล้วส่งต่อไปหาปลายทางจริง (R3 ในตัวอย่างนี้)
08 · จุดที่มักงง

ก็บอกไม่มี MPLS แล้ว ทำไมยังเห็นคำว่า label

เดินตามแพ็กเก็ตทีละ hop ในข้อที่แล้ว จะเห็นว่าตลอดทางไม่มีคำว่า label โผล่มาเลยสักครั้ง แต่พอเปิดคอนฟิกจริงบน Nokia SR OS กลับเจอคำว่า label เต็มไปหมด — คำตอบสั้น ๆ คือ บนสายสัญญาณจริง ไม่มี MPLS label ปนอยู่เลยแม้แต่นิดเดียว แพ็กเก็ตที่วิ่งระหว่างราวเตอร์เป็น IPv6 + SRH ล้วน ๆ ตลอดเส้นทาง — แต่ ภายในตัวราวเตอร์บางรุ่น (ที่ใช้ชิปประมวลผลรุ่นที่มีอยู่แล้วสำหรับ MPLS) ระบบเลือกใช้กลไก lookup table แบบเดียวกับที่ MPLS ใช้อยู่แล้ว มาช่วยค้นหาว่า "เลข LIB นี้ต้องทำอะไร" ให้เร็วขึ้น ซึ่งกลไกนั้นต้องการ "เลข label" เป็นดัชนีค้นหาภายในตัวมันเอง

● บนสาย = IPv6 ล้วน ไม่มี label ● ภายในกล่อง = แปลงเป็น label ชั่วคราว

แพ็กเก็ตที่ออกจากราวเตอร์ยังเป็น IPv6 ล้วนเหมือนเดิมทุกประการ — label เกิดขึ้นแค่ชั่วขณะที่อยู่ในหน่วยประมวลผลภายในกล่องเดียวเท่านั้น ไม่เคยถูกส่งออกไปข้างนอก

สรุปให้จำง่าย

label ที่เห็นในคอนฟิกไม่ใช่ "MPLS แอบแฝงอยู่" แต่เป็นแค่เลขดัชนีภายในฮาร์ดแวร์ ยืมกลไกที่มีอยู่แล้วมาใช้ให้ค้นหาเร็วขึ้นเฉยๆ

09 · กลไกที่ 2

Reserved Label Block: ต้องมีขนาดพอดี LIB แต่ไม่ต้องตรงเลข hex

label ภายในกล่องที่เพิ่งเห็นในข้อที่แล้ว ถูกจับคู่แบบ 1 ต่อ 1 กับทุกค่าใน LIB ระบบเลยต้องมี "คลัง label" (Reserved Label Block) กันไว้ให้ครบพอสำหรับทุกค่าที่ LIB มี — และนี่คือจุดที่คนตั้งค่าใหม่ ๆ มักเข้าใจผิด: คิดว่าตัวเลขในคลัง label ต้องตรงกับค่า hex ของ LIB ด้วย ซึ่งไม่จำเป็นเลย

● LIB (พื้นที่ function จริงในที่อยู่ IPv6) ● คลัง Label ที่จอง (ตัวเลข MPLS label คนละพื้นที่กันเลย)

สองแท่งนี้ยาวเท่ากันเป๊ะ (จำนวน entries เท่ากัน) แต่อยู่คนละช่วงตัวเลขกันโดยสิ้นเชิง — LIB เป็นเลข hex ในที่อยู่ IPv6 (เช่น E000-FFFF) ส่วน label pool เป็นเลข MPLS label ธรรมดา (เช่น 30000-38191) ระบบจับคู่ให้เองภายใน ไม่ต้องให้ตัวเลขตรงกัน

แล้วทำไม GIB ไม่ต้องมีคลัง label บ้าง

GIB บอกแค่ "ราวเตอร์ไหน" — งานของราวเตอร์ตอนเช็คส่วนนี้ คือดูว่า GIB ในแพ็กเก็ตตรงกับค่า un ของตัวเองหรือเปล่า เหมือนเช็คว่าจดหมายส่งถึงบ้านเลขที่ตัวเองไหม ซึ่งเป็นการจับคู่กับ prefix เดียว ที่ตัวเองประกาศออกไปทาง IGP ตามปกติอยู่แล้ว (เหมือน route lookup ทั่วไป) ไม่จำเป็นต้องมีตาราง lookup แยกไว้ล่วงหน้าสำหรับทุกค่า GIB ที่เป็นไปได้ในเครือข่าย เพราะราวเตอร์แต่ละตัวสนใจแค่ค่าของตัวเองค่าเดียว — จึงไม่ต้องมีคลัง label มารองรับส่วนนี้เลย

LIB ต่างออกไปโดยสิ้นเชิง — ค่า LIB แต่ละค่า "ภายในราวเตอร์ตัวเดียวกัน" หมายถึงงานคนละอย่างกัน (คนละ service, คนละปลายทาง, คนละ policy) เมื่อแพ็กเก็ตมาถึงราวเตอร์ที่ถูกต้องแล้ว (GIB ตรงแล้ว) ราวเตอร์ต้องแยกแยะต่อว่า LIB ค่านี้หมายถึงงานไหนในบรรดาหลายสิบหลายพันงานที่มีอยู่ ระบบจึงต้องกันที่ในคลัง label ไว้ให้ครบทุกค่าที่ LIB มีทางเป็นไปได้ทั้งหมดล่วงหน้า ไม่ใช่แค่ค่าที่ใช้งานจริงตอนนั้น

กฎที่ต้องจำ

สิ่งเดียวที่ต้องตรงคือ "จำนวน" (count) — คลัง label ต้องมีจำนวนช่องอย่างน้อยเท่ากับขนาดของ LIB จะเริ่มที่เลขอะไรก็ได้ ขอแค่ไม่ไปชนกับ label range อื่นที่ใช้อยู่ในเครื่องเดียวกัน

10 · ตัวอย่างตัวเลขจริง

ลองคำนวณดูจริง ๆ

รวมทุกกลไกที่ผ่านมาเข้าด้วยกัน จะเห็นว่ามีตัวเลขตัวเดียวที่ต้องเลือก แล้วทุกอย่างคำนวณตามมาหมด — เอาค่านั้นคูณ 1024 จะได้จุดตัดระหว่าง GIB กับ LIB ยิ่งเลือกมาก ยิ่งเผื่อที่ให้ GIB (รองรับราวเตอร์เยอะ) แต่ LIB (และคลัง label ที่ต้องจอง) จะเล็กลงตาม

ค่าที่เลือกจุดตัด (×1024)GIB ≈ รองรับกี่ราวเตอร์LIB ≈ ต้องจอง label กี่ช่อง
16 (ค่าเริ่มต้น) 0x4000 ~16,383 ตัว ~49,151 ช่อง
56 0xE000 ~57,343 ตัว ~8,191 ช่อง
60 (สูงสุด) 0xF000 ~61,439 ตัว ~4,095 ช่อง

เห็น trade-off ชัดเจน: เลือก 60 รองรับราวเตอร์ได้เยอะสุด แต่เหลือที่ให้ทำ function ต่อราวเตอร์แค่ ~4,095 ช่อง — ต้องเลือกให้เหมาะกับขนาดเครือข่ายจริง ไม่ใช่เลือกสูงสุดไว้ก่อนเสมอไป

11 · ข้อควรระวัง

จองน้อยไป ระบบไม่เตือนสักคำ

เห็น trade-off ของการเลือกตัวเลขไปแล้วในข้อที่แล้ว คราวนี้มาดูว่าถ้าคำนวณคลัง label ผิดจะเกิดอะไรขึ้น — ถ้าคลัง label ที่จองไว้เล็กกว่าขนาด LIB จริง คำสั่งตั้งค่าจะผ่านปกติ ไม่มี error ไม่มี warning เลยแม้แต่บรรทัดเดียว — แต่พอมี function ที่ดันไปตกอยู่ในโซนที่ label หมดพอดี prefix ของ function นั้นจะเงียบหายไปเองโดยไม่มีการแจ้งเตือนใด ๆ ต้องมานั่งไล่หาทีหลังว่าทำไม service บางตัวไม่ขึ้น

บทเรียน

ก่อนจองคลัง label ทุกครั้ง ต้องเปิดตารางดูว่าค่าที่เลือกไว้ให้ LIB ขนาดเท่าไหร่ก่อน แล้วจองให้ครบหรือมากกว่านั้นเสมอ — อย่าเดาหรือกะเอาคร่าว ๆ

12 · สรุป

รวมทุกอย่างเข้าด้วยกัน

  • Segment Routing ฝัง "รายการจุดแวะ" ไปกับแพ็กเก็ตตั้งแต่ต้นทาง ไม่ต้องเดาทางทีละ hop
  • SRv6 เอาที่อยู่ IPv6 มาเป็นจุดแวะโดยตรง ไม่มี MPLS label ปนบนสายเลย
  • Micro-SID บีบแต่ละจุดแวะเหลือ 16 บิต ใส่ได้ถึง 8 จุดในที่อยู่เดียว แก้ปัญหา overhead
  • 16 บิตนั้นแบ่งเป็น GIB (ระบุราวเตอร์) กับ LIB (ระบุ function ในราวเตอร์นั้น) ด้วยตัวเลขตัวเดียว
  • ค่าราวเตอร์ (un) ต้องเลือกเองให้อยู่ในโซน GIB เสมอ — CLI ยอมรับตัวเลขกว้างกว่านั้นมาก และไม่เตือนถ้าเผลอหลุดไปโซน LIB
  • label ที่เห็นในคอนฟิกเป็นแค่กลไก lookup ภายในฮาร์ดแวร์บางรุ่น ไม่เคยออกไปบนสายจริง
  • GIB ไม่ต้องมีคลัง label เพราะแค่จับคู่กับ prefix เดียวของตัวเองผ่าน IGP ตามปกติ แต่ LIB ต้องมี เพราะแต่ละค่าคืองานคนละอย่างที่ต้องแยกแยะแบบ index ต่อค่า
  • คลัง label ต้องมี จำนวน ครบเท่า LIB เสมอ แต่ ตัวเลขไม่ต้องตรงกับ hex ของ LIB — จองผิดขนาดแล้วไม่มี warning ให้เห็นด้วย ต้องคำนวณเองให้ครบตั้งแต่แรก
