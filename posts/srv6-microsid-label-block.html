Nokia SR OS กับ
SRv6 Micro-SID

SRv6 ไม่ต้องพึ่ง MPLS แต่พอเปิด config Micro-SID บน Nokia SR OS กลับเจอ mpls-labels และ reserved-label-block เต็มไปหมด โพสต์นี้แบ่งเป็น 2 ส่วน: ส่วนแรกปูพื้น SRv6 กับ Micro-SID จากศูนย์ (ลาก slider ดูการแบ่ง GIB/LIB และเดินแพ็กเก็ตทีละ hop เองได้) ส่วนที่สองลงเรื่อง label space บน SR OS ว่าต้องจองเท่าไหร่ ตรวจสอบยังไง และพลาดตรงไหนแล้วระบบเงียบ จากผลแล็บจริง

เลื่อนลงเพื่อเริ่มเรียนรู้
01 · SRv6 กับ Micro-SID

Segment Routing: ต้นทางเขียนเส้นทางให้ทั้งหมด

Segment Routing ให้เราเตอร์ต้นทางเขียน "รายการจุดแวะ" ทั้งหมดแนบไปกับแพ็กเก็ตตั้งแต่แรก เราเตอร์ระหว่างทางแค่ทำตามรายการ ไม่ต้องเดาทางเองทีละ hop แบบ routing เดิม

01

ต้นทางตัดสินใจ

เราเตอร์ต้นทางเลือกเส้นทางทั้งหมดล่วงหน้า ไม่ปล่อยให้แต่ละจุดตัดสินใจเอง

02

รายการฝังไปกับแพ็กเก็ต

"จุดแวะ" (segment) ทุกจุดถูกเขียนแนบไปกับแพ็กเก็ตเอง ไม่ต้องมีใครจำเส้นทางไว้ล่วงหน้า

03

แต่ละจุดทำตามคิวถัดไป

เราเตอร์ระหว่างทางแค่มองจุดแวะถัดไปในรายการ ทำตามแล้วส่งต่อ ไม่ต้องคิดอะไรเพิ่ม

  • เครือข่ายแบบเดิม: แต่ละเราเตอร์ตัดสินใจเองทีละ hop เหมือนถามทางที่สี่แยกไปเรื่อย ๆ
  • Segment Routing: ตัดสินใจครั้งเดียวที่ต้นทาง แล้วฝังรายการจุดแวะ (segment) ไปกับแพ็กเก็ต ไม่ต้องให้เราเตอร์กลางทางจำ state ของเส้นทางไว้
02 · SRv6 กับ Micro-SID

SRv6: จุดแวะแต่ละจุดคือ IPv6 address หนึ่งตัว

SRv6 (Segment Routing over IPv6) ใช้ IPv6 address หนึ่งตัวแทนจุดแวะหนึ่งจุด เก็บรายการทั้งหมดไว้ใน SRH (Segment Routing Header) จึงไม่ต้องมี MPLS label บนสายเลย

● Locator (เราเตอร์ไหน) ● Function (ทำอะไร)
  • SRH เป็น IPv6 extension header อยู่ต่อจาก IPv6 header ทันที ก่อนถึง payload (ไม่ใช่ต่อท้ายแพ็กเก็ต)
  • address แต่ละตัวแบ่งเป็น 2 ส่วน: Locator (เราเตอร์ไหน) และ Function (ทำอะไรที่นั่น)
  • ทุกครั้งที่ผ่านเราเตอร์ ค่า Segments Left ลดลง 1 แล้วที่อยู่ปลายทาง (DA) ถูกเปลี่ยนให้ชี้ไปจุดแวะถัดไป ส่วนรายการใน SRH ยังอยู่ครบ ไม่ถูกลบ
  • ยกเว้นเปิด PSP/USP ซึ่งอนุญาตให้ตัด SRH ทิ้งเมื่อถึงจุดท้าย ๆ ของเส้นทาง

สี่เหลี่ยมเล็กด้านบนในภาพคือตัวนับ Segments Left ที่เหลืออยู่ ไม่ใช่รายการที่ถูกตัดทิ้ง

03 · SRv6 กับ Micro-SID

ปัญหา overhead และทางแก้ด้วย Micro-SID

address เต็ม 128 บิตต่อจุดแวะทำให้ SRH ยาวขึ้นตามความซับซ้อนของเส้นทาง Micro-SID (uSID) แก้ด้วยการบีบแต่ละจุดแวะให้เหลือ 16 บิต แล้วเรียงหลายจุดไว้ใน address เดียว

ปัญหา: ยิ่งเส้นทางซับซ้อน ยิ่งต้องแบกรายการยาว

● ขนาด SRH ที่ต้องแบก
  • IPv6 address หนึ่งตัวยาว 128 บิต เส้นทาง 6 จุดแวะ = 6 × 128 = 768 บิต เฉพาะส่วนหัว
  • ยิ่งทำ traffic engineering ละเอียด รายการยิ่งยาว กินทั้งพื้นที่ในแพ็กเก็ตและแรงประมวลผลทุก hop

ทางแก้: Micro-SID บีบจุดแวะเหลือช่องละ 16 บิต

● แบบเดิม (1 จุดแวะ/128 บิต) ● Micro-SID (block 32 บิต + 6 ช่อง)
  • 128 บิตไม่ได้ว่างทั้งก้อน ส่วนหน้าต้องกันไว้ให้ SID block (prefix ที่ใช้ร่วมกันทั้งโดเมน) ก่อนเสมอ ที่เหลือจึงซอยเป็นช่องละ 16 บิต
  • จำนวนช่อง = (128 − block length) ÷ 16 ไม่ใช่ 128 ÷ 16: block /32 ได้ 6 ช่อง, block /48 ได้ 5 ช่อง
  • ตลอดโพสต์นี้ใช้ block 2001:bbbb::/32 ตรงกับ config ที่ทดสอบจริง จึงมี 6 ช่องต่อ address
  • ถ้าเส้นทางยาวเกินจำนวนช่อง ให้ต่อ address ก้อนถัดไปใน SRH เพิ่ม
04 · SRv6 กับ Micro-SID

GIB กับ LIB: แยกด้วยช่วงตัวเลข และวิธีตั้งเลขเราเตอร์ (un)

ทุกช่อง 16 บิตมีความหมายเดียวทั้งช่อง เป็นได้ทั้ง GIB (เลขประจำเราเตอร์) หรือ LIB (เลขงานภายในเราเตอร์) ตัดสินจากค่าตัวเลขในช่องนั้นว่าตกอยู่ช่วงไหน ไม่ใช่การแบ่งบิตภายในช่อง

● GIB — เลขประจำเราเตอร์ (เราเตอร์ไหน) ● LIB — เลขงานภายในเครื่อง (ทำอะไรในเราเตอร์นั้น)

  • ถ้า GIB กับ LIB ทับกัน แพ็กเก็ตที่ตั้งใจส่งไปหาเราเตอร์ที่มี un เท่ากับเลขนั้น จะถูกเครื่องนี้ดักกินเป็น function ของตัวเองทันที

05 · SRv6 กับ Micro-SID

เดินตามแพ็กเก็ตทีละ hop

06 · Label space บน SR OS

ไม่มี MPLS แล้ว ทำไม config ยังเต็มไปด้วยคำว่า label

บนสายไม่มี MPLS label เลย แพ็กเก็ตเป็น IPv6 + SRH ล้วนตลอดทาง คำว่า label ใน config ของ SR OS คือดัชนี lookup ภายในเราเตอร์ที่ยืมกลไกของชิป MPLS เดิมมาใช้

● บนสาย = IPv6 ล้วน ไม่มี label ● ภายในกล่อง = แปลงเป็น label ชั่วคราว
  • เราเตอร์ FP-based ใช้ lookup table แบบเดียวกับ MPLS เพื่อหาว่า "ค่า LIB นี้ต้องทำอะไร" และ table นั้นใช้เลข label เป็นดัชนี
  • label เกิดขึ้นชั่วขณะในหน่วยประมวลผลของกล่องเดียว แพ็กเก็ตที่ออกจากเราเตอร์ยังเป็น IPv6 ล้วนเหมือนเดิม
  • จึงไม่ใช่ "MPLS แอบแฝง" แต่เป็นที่มาของ mpls-labels reserved-label-block ที่ต้องจองให้ Micro-SID
07 · Label space บน SR OS

Reserved Label Block ต้องใหญ่แค่ไหน

ค่า LIB ทุกค่าที่ใช้งานจริงต้องมี label ภายในคู่กัน 1 ต่อ 1 จึงต้องจอง reserved-label-block ให้จำนวนพอ ส่วนตัวเลข label ไม่ต้องตรงกับค่า hex ของ LIB ระบบจับคู่ให้เองภายใน

● LIB (พื้นที่ function จริงในที่อยู่ IPv6) ● คลัง Label ที่จอง (ตัวเลข MPLS label คนละพื้นที่กันเลย)
  • แท่งสองแท่งยาวเท่ากัน (จำนวน entries เท่ากัน) แต่คนละช่วงตัวเลข: LIB เป็น hex ใน address (เช่น E000–FFFF) ส่วน label เป็นเลข MPLS ธรรมดา (เช่น 30000–38191)
  • เริ่มที่เลข label อะไรก็ได้ ขอแค่ไม่ชนกับ label range อื่นในเครื่องเดียวกัน

ทำไม GIB ไม่ต้องมี label block

  • GIB: เราเตอร์เช็คแค่ว่าช่องนั้นตรงกับ un ของตัวเองไหม เป็นการ match กับ prefix เดียวที่ประกาศผ่าน IGP เหมือน route lookup ปกติ ไม่ต้องมี table แยกสำหรับทุกค่า GIB ในเครือข่าย
  • LIB: แต่ละค่าในเราเตอร์เดียวกันคืองานคนละอย่าง (คนละ service, ปลายทาง, policy) ต้องแยกแยะเป็นรายค่า จึงต้องมี label รองรับทุก function ที่จะใช้ ทั้ง static และ dynamic

ขนาดที่ถูกต้องมี 3 ชั้น: LIB คือ "เพดาน" ไม่ใช่ "พื้น"

  • พื้นแข็ง: ต้อง ≥ static-function max-entries ถ้าไม่ถึง CLI reject ทันที
  • พื้นใช้งานจริง: ควร ≥ max-entries + จำนวน dynamic function ที่คาดว่าจะใช้ (VPRN, uA auto-allocate ฯลฯ) จุดนี้ไม่มี CLI เช็คให้ ขาดแล้วเงียบ (หัวข้อ 10)
  • เพดาน: ขนาด LIB เต็ม = 2^16 − global-sid-entries × 1024 จองเกินนี้ไม่ผิดกฎ แต่เสีย label เปล่า คู่มือ Nokia เขียนไว้ว่า "a label-block should not need exceed that value"
  • สิ่งเดียวที่ต้องตรงกันคือจำนวน ระหว่าง label block กับ function ที่ใช้จริง ไม่ใช่ตัวเลข และไม่ใช่ขนาด LIB เต็ม

global-sid-entries กำหนดเพดานของ LIB

ค่าที่เลือกจุดตัด (×1024)GIB ≈ รองรับกี่เราเตอร์LIB = เพดานของ label block
16 (ค่าเริ่มต้น) 0x4000 16,383 ตัว 49,152 ช่อง
56 0xE000 57,343 ตัว 8,192 ช่อง
60 (สูงสุด) 0xF000 61,439 ตัว 4,096 ช่อง
  • เลือก 60 รองรับเราเตอร์ได้มากสุด แต่เหลือที่ให้ function ต่อเราเตอร์แค่ 4,096 ค่า ต้องเลือกให้เหมาะกับขนาดเครือข่ายจริง
  • เพดานที่ global-sid-entries 16 คือ 49,152 label ต่อหนึ่ง block ≈ 9.4% ของ label space ทั้งเครื่อง (524,288) ถ้ามีหลาย locator หรือหลาย Flex-Algorithm ที่ต้องแยก block การจองเต็มเพดานทุกก้อนจะกิน label ของเครื่องเร็วมาก
  • ในทางปฏิบัติ: จองตามจำนวน function ที่วางแผนใช้จริง + headroom แล้วไม่เกินเพดาน
08 · Label space บน SR OS

static-function: ผ่า LIB เป็นโซน static กับ dynamic

static-function max-entries แบ่ง LIB อีกชั้น: index 1 ถึง max-entries คือโซน static ที่ operator กำหนดค่าเอง (ได้ค่าเดิมเสมอแม้ reboot) ส่วนที่เหลือคือโซน dynamic ที่ระบบเลือกช่องว่างให้เอง

  • ต้องเป็น static เพราะมีคนอื่นอ้างค่าตรง ๆ: uA ที่กำหนดเอง, service micro-SID ที่ระบุ value (uDT4/uDT6/uDT46/uDX2/uDX6) และ binding-SID (uB6) ของ SRv6 policy ทั้งสามชนิดใช้โควตา static เดียวกัน
  • un (GIB) ไม่กินโควตานี้ เพราะอยู่คนละ pool ตั้งแต่ต้น
  • โซน dynamic เริ่มที่ LIB start + max-entries พอดี: ตั้ง max-entries 16 แล้ว uDT46 ตัวแรกที่ระบบจัดให้ได้ 0x4010 (16400) โซน static จึงเป็น 0x4000–0x400F
configure router "Base" segment-routing segment-routing-v6
    base-routing-instance micro-segment-locator "aa"
        function
            ua 1 interface-name "to_xxx"

เลข 1 ท้าย ua ไม่ใช่ค่า hex ของ LIB แต่เป็น index ในโซน static ระบบเอาไปบวกกับจุดเริ่มของ LIB ให้เอง

สูตรที่วัดจากแล็บ SR-SIM 26.3.R1

Oper Func = (global-sid-entries × 1024) + (index − 1)

  • ua 1 / 2 / 3 ที่ global-sid-entries 16 ได้ SID ลงท้าย 4000:: / 4001:: / 4002:: (16384 / 16385 / 16386) คือ index 1 = จุดเริ่ม LIB พอดี
  • เปลี่ยน global-sid-entries เป็น 56 โดยไม่แตะ config uA: ค่าทั้งชุดขยับเป็น e000:: / e001:: / e002:: ทันที ยืนยันว่า index ผูกกับจุดเริ่มของ LIB
  • service SID ใช้สูตรเดียวกันทุกชนิด: udt46 value 5, udx2 6, udt4 7, udt6 8, udt2u 9, udt2m 10 ได้ 4004:: … 4009:: ตามลำดับ ตรงกับตัวอย่างใน Advanced Configuration Guide (udx2 value 5 → 4004::)
  • index ใช้ pool เดียวกันทั้ง block: ชนกันข้ามชนิด function, ข้าม uA และข้ามทุก locator ที่ใช้ block เดียวกัน ระบบ reject แม้ SID สุดท้ายจะไม่ซ้ำกันบนสาย (คนละ un) จึงต้องวางแผน index ร่วมกันทั้งโดเมน
  • binding-SID (uB6) ที่ head-end รับต้องอยู่ในรูปเต็ม <block><uN><uB6> เสมอ ส่งค่า uB6 ลอย ๆ ช่องเดียวไม่ได้ (entry สั้นใน FIB ใช้ได้เฉพาะตอนแพ็กเก็ตเลื่อนมาถึงตำแหน่งนั้นแล้ว)
  • ค่าเริ่มต้นของ max-entries คือ 1 จะใช้ static function มากกว่า 1 ตัวต้องปรับเอง
  • แก้ max-entries ทีหลัง = block ทั้งก้อน admin-state toggle อัตโนมัติ (ตาม CLI warning) service ทุกตัวบน block นั้นสะดุด ต้องวางแผนจำนวน static ให้ครบตั้งแต่วันแรก

10 · Label space บน SR OS

จอง label block น้อยไปแล้วเกิดอะไร

ละเมิดโซน static ส่วนใหญ่ CLI reject ทันทีตอน commit แต่ถ้าโซน dynamic หมด ทุกอย่างเงียบ: commit ผ่าน service ขึ้น Up แต่ไม่มี SID และ VPN นั้น blackhole

กรณีที่ CLI reject ให้

  • ลด max-entries ต่ำกว่าจำนวน static ที่ใช้อยู่ → MINOR: MGMT_CORE #4001: ... Cannot configure function value as it is exceeding max entries
  • ตั้ง static index เกิน max-entries (เช่น ua 17 ตอน max-entries 16) → error เดียวกัน
  • ย่อ label block ให้เล็กกว่า max-entries → MINOR: MGMT_CORE #4001: ... Start and end labels range 2 must be more than max-entries

กรณีที่เงียบ: โซน dynamic หมด

  • สร้าง service ใหม่ที่ต้องการ dynamic function เมื่อ block เหลือที่ไม่พอ → commit ผ่าน, service ขึ้น Admin/Oper Up, แต่ไม่มี SID เกิดขึ้น
  • หลักฐานเดียวคือ log ระดับ MINOR: SVCMGR #2135 "Allocation of function failed for vprn ... function udt46 value 0."

  • ค่าที่ตั้ง static เอง (เช่น udt46 value 5) ไม่เคยขยับ เพราะระบบ reallocate ได้เฉพาะ dynamic

Checklist สรุป

  • SRv6 ใช้ IPv6 address เป็นจุดแวะ รายการอยู่ใน SRH ไม่มี MPLS label บนสาย
  • Micro-SID บีบจุดแวะเหลือช่องละ 16 บิต จำนวนช่อง = (128 − block length) ÷ 16 (block /32 = 6 ช่อง)
  • ทุกช่องเป็น GIB (เราเตอร์) หรือ LIB (function) ตามช่วงตัวเลข จุดตัด = global-sid-entries × 1024 ตั้งเท่ากันทั้งโดเมน
  • un value ต้องน้อยกว่าจุดตัดและไม่ซ้ำ CLI ไม่เช็คให้
  • label ใน config เป็นดัชนี lookup ภายในเครื่อง ไม่เคยออกไปบนสาย
  • GIB ไม่ต้องมี label block (match prefix เดียวผ่าน IGP) แต่ LIB ต้องมี label 1 ต่อ 1 กับทุก function ที่ใช้
  • ขนาด label block: ≥ max-entries (ไม่ถึง CLI reject), ควร ≥ max-entries + dynamic ที่คาด (ขาดแล้วเงียบ), ไม่จำเป็นต้องจองเต็ม LIB และตัวเลข label ไม่ต้องตรงกับ hex ของ LIB
  • static-function: index 1..max-entries เป็น static (uA, service SID ที่ระบุ value, uB6 ใช้โควตาร่วมกัน) Oper Func = LIB start + index − 1, default max-entries = 1
  • uB6 ต้องอ้างแบบเต็ม <block><uN><uB6>
  • dynamic หมด = commit ผ่าน service Up แต่ไม่มี SID มีแค่ log SVCMGR #2135 และ PE อีกฝั่งจะไม่เห็น route ของ service นั้น
  • แก้ max-entries หรือขนาด block ทีหลัง = block toggle และ dynamic SID เลื่อน เป็น service-affecting ต้องมี maintenance window
  • block ขนาด N ใช้ dynamic ได้ N − 1 เสมอ
