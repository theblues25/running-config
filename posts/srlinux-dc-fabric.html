1. Nokia Data Center Fabric Solution

1.1 Modern DC Architecture

สาระสำคัญ

  • DC แบบเดิม (3-tier): Core (L3) / Aggregation + Access (L2) ออกแบบมาเพื่อ client-server → traffic ส่วนใหญ่เป็น north-south
  • ปัญหาของ 3-tier:
    • scale ยาก (ต้องซื้อ aggregation ตัวใหญ่ขึ้น)
    • ใช้ STP → link สำรองถูก block
    • east-west วิ่งอ้อม (hairpin ผ่าน aggregation)
    • กระจาย traffic ไม่สม่ำเสมอ
    • troubleshoot ยาก
  • Leaf-Spine (Clos): leaf ทุกตัวต่อกับ spine ทุกตัว
    • ใช้ L3 + ECMP กระจาย traffic บน link ที่ขนานกัน
    • path ของ east-west คงที่/คาดเดาได้ (จำนวน hop เท่ากันเสมอ) → troubleshoot ง่าย
    • เพิ่ม uplink capacity ได้โดยเพิ่ม spine
  • Scale ต่อ: เพิ่มชั้น super-spine
    • leaf+spine full mesh 1 ชุด = 1 cluster แล้ว super-spine เชื่อมหลาย cluster
    • ข้อเสียคือ cabling เยอะ
  • Underlay vs Overlay:
    • underlay = เครือข่าย IP กายภาพ (leaf-spine)
    • overlay = VPN เสมือนบน underlay เพื่อแยก tenant (multi-tenant DC)
  • Routing ของ underlay: OSPF/IS-IS ใช้ได้ แต่ BGP เป็นที่นิยม เพราะ
    • อาจ efficient กว่า link-state (topology change ไม่ flood ไปทั้ง domain)
    • mature/เข้าใจกันดี
    • รองรับ IPv4+IPv6
    • ข้อเสียคือ config เยอะ → ต้อง automate
  • แนวทาง BGP-only DC (RFC 7938):
    • ไม่มี IGP
    • eBGP ดีกว่า iBGP
    • ใช้ private ASN
    • ลด timer ให้ converge เร็ว (default ของ SP เน้นเสถียร)
    • RFC 8950 = BGP บน unnumbered interface (IPv4 NLRI + IPv6 next-hop)
  • ถ้าเป็น multi-tenant (EVPN-VXLAN): BGP ทำ 2 หน้าที่ คือ underlay routing และ EVPN control plane
    • session EVPN แยกจาก underlay (มักใช้ route reflector)

สรุปที่ควรจำ — ASN design

ชั้น กฎ ตัวอย่าง
Leaf แต่ละ leaf ASN ไม่ซ้ำกัน 65101…65106, 65201…65206
Spine ใน cluster เดียวกัน ASN เดียวกันทั้ง cluster cluster1 = 65100
Spine ต่าง cluster ASN ต่างกัน cluster2 = 65200
Super-spine ASN เดียวกันทั้งหมด (แต่ต่างจาก spine) 65000
  • เหตุผล: กำหนด ASN ผิดแบบ → sub-optimal routing ตอน link/node fail
    • spine ใน cluster ใช้ ASN เดียวกัน → AS-path loop prevention ทำให้ route ไม่วิ่ง leaf→spine→leaf→spine อ้อม
    • leaf ใช้ ASN ต่างกัน → leaf ไม่ทิ้ง route ของ leaf อื่น
  • Private ASN: 2-byte 64512–65534, 4-byte 4,200,000,000–4,294,967,294
  • VXLAN: tunnel ที่ใช้มากที่สุดใน DC (RFC 7348)
    • VTEP = จุด encap/decap มักเป็น leaf หรือ DC gateway (หรือ hypervisor ก็ได้)
  • EVPN (RFC 8365): control plane มาตรฐานสำหรับสร้าง/ลบ VXLAN tunnel แบบ dynamic (static ก็ได้แต่ไม่ scale)
    • ทำ auto-discovery ของ remote VTEP
    • เรียนรู้/กระจาย MAC/IP
    • ต้องการ BGP full-mesh ระหว่าง VTEP → ใช้ RR (บน spine หรือเป็น app บน server)
  • Nokia DCF solution = 3 ส่วน:
    • hardware 7220/7250 IXR (merchant silicon)
    • SR Linux NOS
    • EDA (automation)

เทียบ SR OS: SP core ปกติใช้ IGP (IS-IS) + iBGP/RR; DC แบบ RFC 7938 กลับกัน — eBGP ทุก hop ไม่มี IGP, ASN ต่อ leaf คล้ายใช้ ASN เป็น "router-id" ของ path

1.2 Introduction to SR Linux

สาระสำคัญ

  • คุณสมบัติหลัก:
    • unmodified Linux kernel (ง่ายต่อ app 3rd-party)
    • open + model-driven (YANG)
    • modular state-driven NOS
    • protocol stack มาจาก SR OS (เช่น BGP)
    • CLI plugin (Python) ปรับ CLI ได้ทั้งหมด
    • NDK (NetOps Development Kit) สำหรับ app 3rd-party
    • streaming telemetry
  • สถาปัตยกรรม:
    • ทุก function (BGP, IS-IS, LLDP, …) = Linux application แยกกัน
    • แต่ละ app มี YANG model ของ config+state
    • เข้าถึงผ่าน CLI, JSON-RPC, gNMI/gRPC
    • app คุยกันผ่าน IDB (impart database) แบบ pub/sub, ข้อมูลเป็น protobuf (name:value pair, language/platform neutral)
    • app 3rd-party ใช้ API/IDB ได้ เท่ากับ app ของ Nokia
  • YANG: RFC 6020 (เดิมทำเพื่อ NETCONF), เป็น tree แปลงเป็น JSON/XML ได้
    • container = branch, leaf = data
    • จุดที่มักสับสน: อย่าสลับ container กับ leaf
  • app_mgr:
    • อ่าน config (YAML) ใน /opt/srlinux/appmgr/ แล้ว start ทุก app
    • จัดการ app 3rd-party ที่วางไว้ใน directory เดียวกันด้วย
    • monitor health + restart
    • โหลด YANG model เข้า mgmt_svr
  • IDB: ศูนย์กลางการสื่อสารระหว่าง app, application-independent / protocol-neutral
    • แบ่งเป็น topic — แต่ละ topic มีเจ้าของ app เดียว
    • app publish เป็น protobuf, app อื่น subscribe และถูก notify เมื่อเปลี่ยน
  • mgmt_svr: เป็นเจ้าของ YANG ของทุก app
    • validate config แล้วแปลง YANG → protobuf ลง IDB
    • (หน้าที่นี้เป็นของ mgmt_svr ไม่ใช่ app_mgr)
  • CLI: เป็น app หนึ่ง เขียนด้วย Python (open source)
    • รองรับ plugin สร้าง show/tools command เองจาก YANG
    • มี alias, env var, autocompletion, range, wildcard
  • Hardware:
    • 7220 IXR-D1/D2/D2L/D3/D3L → leaf/ToR (D3 ใช้เป็น spine ได้)
    • 7220 IXR-H2 (128x100G) / H3 (32x400G) → spine
    • 7250 IXR-6/10 → spine/super-spine (chassis, control/fabric redundant)
    • MPLS/SR = 7250 IXR เท่านั้น, EVPN-VXLAN = 7220 IXR-D2/D2L/D3/D3L
    • XDP (eXtensible Data Path) = abstraction ของ chipset ให้ IDB/app → เพิ่ม hardware ใหม่ได้โดยไม่กระทบ NOS

เทียบ SR OS: SR OS เป็น monolithic NOS (TiMOS) — ไม่มี IDB/pub-sub ให้ user เห็น; SR Linux คือแนวคิด "ทุกอย่างเป็น Linux process + YANG" ส่วน MD-CLI ของ SR OS ก็ model-driven เหมือนกันแต่ไม่ได้เปิดให้เขียน plugin แบบ Python ในตัว CLI

1.3 Intro to EDA

  • ความต้องการของ DC ใหญ่: automate ทุกอย่าง, scale แบบเรียบง่าย, customize ต่อ tenant, security
    • → จัดการ DC network เป็น unified switch fabric ตัวเดียว
  • EDA: toolkit automate DC fabric
    • อยู่บน Kubernetes
    • ใส่ข้อมูลน้อยที่สุดสำหรับ fabric design
    • closed-loop (เฝ้า state ให้ตรง intent)
    • digital sandbox ลดความเสี่ยงของ change
    • integrate กับ cloud platform
  • EDA operations ครอบ Day 0 design / Day 1 deployment / Day 2+ operation:
    • Fabric intent = config state ของ fabric แบบ declarative YAML, รองรับ CI/CD, validate บน digital sandbox
    • Fabric operations = intent + streaming telemetry แสดงในบริบทเดียวกัน
    • Fabric observability = GUI แสดง performance จาก on-change/streaming telemetry
    • Fabric integration = plugin model กับ OpenShift, VMware

สรุปท้ายหัวข้อ

  • Clos = east-west path คงที่ + L3/ECMP + scale ได้ยืดหยุ่น
  • protocol ที่แนะนำสำหรับ underlay = eBGP
  • leaf = ASN ไม่ซ้ำ
  • routing function = Linux application แยกแต่ละตัว
  • IDB publish ข้อมูลเป็น protobuf
  • EDA อยู่บน Kubernetes

2. SR Linux Configuration and Routing

2.1 CLI Basics

สาระสำคัญ

  • mgmt_svr = จุดศูนย์กลางของ client ทั้งหมด (CLI, gNMI, JSON-RPC คุยกับ mgmt_svr ผ่าน gRPC)
    • enforce YANG แล้วเขียน config ลง IDB
  • CLI: เข้าได้ทาง SSH หรือ console
    • command tree สร้างจาก YANG (container + leaf) จึง เหมือนกันทั้ง CLI/gNMI/JSON-RPC
    • แสดงผลเป็น JSON ได้, รองรับ plugin
    • leaf มีค่าเดียว (เช่น host-name), container จัดกลุ่ม node ไม่มีค่าในตัวเอง
  • การเข้าใช้:
    • console 115200 8N1 no flow control
    • SSH เปิดบน mgmt โดย default (factory config)
    • default user admin/admin
    • ออกด้วย Ctrl+D หรือ quit
  • Prompt 2 บรรทัด: --{ <flags> <mode> }--[ <context> ]-- + A:hostname# และ bottom toolbar (mode, user, session id, เวลา)
  • Help:
    • ? = command ใน context นี้/usage
    • help = อธิบาย mode ปัจจุบัน
    • tree = โครง node
  • Navigate:
    • exit ขึ้น 1 ชั้น
    • exit all หรือ / กลับ root
    • .. ขึ้นชั้น (ใช้กับ info ได้)
    • { } เข้า/ออก context
  • History:
    • history / history hot (top 20) / history context / history clear
    • !8 เรียกคำสั่งที่ 8, Ctrl+R reverse search
    • password ไม่โชว์ใน history; ไฟล์ ~/.srlinux_history
  • bash = เข้า Linux shell (ออกด้วย Ctrl+D/logout), หรือ bash <cmd> รันคำสั่งเดียว
  • Output redirection > (overwrite) / >> (append) ไปไฟล์ใน home dir
  • pipe ไป grep / more / head / tail / wc และ utility ของ SR Linux: | as json|table|text, | filter fields ...

Candidate / transaction

  • แก้ใน candidate → ไม่ต้องเรียงลำดับ config → commit → validate 3 ขั้น:
    • (1) YANG validation
    • (2) application validation
    • (3) forwarding-plane/resource validation
    • ขั้นไหน fail = ไม่ commit ทั้งก้อน
  • candidate datastore อยู่ต่อแม้ logout จนกว่าจะ commit หรือ discard
  • คำสั่ง:
    • commit validate = ตรวจอย่างเดียวไม่ apply
    • commit now = apply แล้วกลับ running; commit stay = apply แล้วอยู่ candidate ต่อ
    • commit save = apply + save เป็น startup (/etc/opt/srlinux/config.json)
    • commit confirmed [timeout N] = apply ชั่วคราว ต้อง commit confirmed accept ภายในเวลา ไม่งั้น auto rollback (default 600 วินาที = 10 นาที)
    • ใช้กัน lock ตัวเองจาก ACL/route ผิด
    • commit checkpoint name X comment Y = commit + สร้าง checkpoint
    • discard now / discard stay = ทิ้งการแก้ไขตั้งแต่ commit ล่าสุด
    • diff = ดูสิ่งที่เปลี่ยน
  • Prompt flags:
    • * = candidate มีการแก้ที่ยังไม่ commit
    • + = running ต่างจาก startup (ยังไม่ save)
    • ! = (private candidate) running เปลี่ยนไปจาก baseline ของเรา เพราะคนอื่น commit

    • ตอนเข้า, running ถูก copy ไปทั้ง baseline และ candidate

สรุปที่ควรจำ — Checkpoint

  • checkpoint = running config เก็บเป็น JSON ใน /etc/opt/srlinux/checkpoint/checkpoint-N.json
  • default เก็บได้ 10 (range 1..255)
    • checkpoint 0 = ล่าสุดเสมอ, อันเก่าถูก renumber +1
    • เกิน max → ลบอันเก่าสุด
  • revert ได้ทุก checkpoint ที่มีอยู่ (ไม่ใช่แค่อันล่าสุด) — ต้องอยู่ candidate mode ก่อน
  • auto-checkpoint (สร้างทุก commit) default = false
  • คำสั่งสร้าง: commit checkpoint name ... comment ..., save checkpoint, tools system configuration generate-checkpoint [name ..] [comment ..]
  • ดู: info from state detail system configuration checkpoint * | as table
  • revert/clear:
A:spine1# enter candidate
A:spine1# tools system configuration checkpoint 0 revert
    Successfully reverted configuration
A:dc-leaf-1# tools system configuration checkpoint 2 clear

สรุปที่ควรจำ — ไฟล์ config / startup / rescue

  • source <file> [auto-commit] = รันคำสั่งจากไฟล์ทีละบรรทัด (default จาก home dir; ใช้รูปแบบ flat จะรันได้จากทุก context)
  • save file <name> [detail] [from running|state] [text] = save datastore เป็นไฟล์ (default JSON ใน home) — ไม่ได้ทำให้เป็น startup
  • ทำเป็น startup: commit save หรือ save startup หรือ tools system configuration save → /etc/opt/srlinux/config.json (เครื่องหมาย + หาย)
  • Rescue: ลำดับตอน boot
    • ใช้ config.json ก่อน
    • ถ้า fail ใช้ rescue (/etc/opt/srlinux/checkpoint/rescue-config.json, สร้างด้วย save rescue / tools system configuration rescue-save)
    • ถ้าไม่มี/fail อีก สร้าง factory config (mgmt0.0 DHCP v4/v6 + network-instance mgmt + SSH)
  • delete <container|leaf> ต้องอยู่ candidate
    • ลบ container = ลบทั้ง subtree
    • ลบ leaf ที่มี default = กลับเป็นค่า default

ไฟล์สำคัญใน Linux

  • /etc/opt/srlinux/config.json (startup)
  • /etc/opt/srlinux/checkpoint/
  • /opt/srlinux/bin (apps)
  • /var/log/srlinux/buffer (tmpfs = RAM)
  • /var/log/srlinux/file (persistent)

2.2 Interfaces, LLDP, LAG

สาระสำคัญ

  • ประเภท interface:
ประเภท ชื่อ หมายเหตุ
Loopback lo<0..255> (max 256) virtual, always up, ใช้กับ BGP
System system0 (มีได้ subinterface เดียว system0.0) always up, จำเป็นสำหรับ VXLAN tunnel (VTEP address)
Management mgmt0 มีได้ 1 ต่อเครื่อง, physical OOB, active/standby บน chassis (2 CPM)
Network ethernet-<slot>/<port>[/<breakout>] 7220 แบบ fixed: slot = 1 เสมอ; IXR-6/10 มี 4/8 linecard
LAG lag<N>
IRB irb<0..255> L3 internal interface เชื่อม mac-vrf ↔ ip-vrf
  • interface = L2 (speed, MTU, vlan-tagging, LAG membership ethernet aggregate-id, transceiver, breakout) / subinterface = L3 (IPv4/IPv6, ip-mtu, VLAN id)
  • interface ที่สร้างใหม่ admin-state enable โดย default
  • Breakout: เช่น IXR-D3 QSFP28 → breakout-mode num-channels 4 channel-speed 25G → ได้ ethernet-1/3/1..4
  • Subinterface:
    • ชื่อ <parent>.<index> โดย index อยู่ในช่วง 0..9999
    • type default = routed (อีกแบบ = bridged สำหรับ mac-vrf)
    • static IP กับ DHCP client ใช้พร้อมกันไม่ได้
    • ถ้าจะมีมากกว่า 1 subinterface ต้องเปิด vlan-tagging
  • IP:
    • ได้สูงสุด 16 IPv4 + 16 IPv6 subnet ต่อ subinterface
    • primary = source ของ broadcast/multicast — ตั้งเอง หรือระบบเลือก IP ต่ำสุด
  • VLAN:
    • vlan-tagging true ที่ interface, vlan encap single-tagged vlan-id X ที่ subinterface
    • VLAN 1..4094; เนื้อหาตรงนี้ครอบคลุมเฉพาะ single tag; VLAN มีความหมายแค่ local
    • index ไม่จำเป็นต้องเท่ากับ VLAN (best practice: untagged = .0, tagged = index เท่ากับ VLAN)
    • bridged เท่านั้น: encap untagged (รับ frame ไม่มี tag บน port ที่เปิด tagging) และ vlan-id optional (default subinterface รับ VLAN ที่ไม่ match ที่อื่น, ไม่ strip tag)
  • show vs info:
    • show interface (เฉพาะที่ up), show interface all, show interface X detail
    • info detail interface X (config + default), info from state interface X (config + oper + stats), | as table
  • ผิด prefix length: /32 บน ethernet subinterface → commit fail "ipv4 prefix length 32 not supported on this interface type" (ต้องลบอันผิดก่อน เพราะมีหลาย IP ได้)
A:leaf1# interface ethernet-1/10 vlan-tagging true subinterface 0 type bridged vlan encap untagged
A:leaf1# interface lo0 subinterface 0 ipv4 address 100.0.2.1/32
A:leaf1# interface lo0 subinterface 0 ipv4 admin-state enable
  • ระวัง: ต้อง ipv4 admin-state enable ที่ subinterface ด้วย

LLDP

  • IEEE 802.1AB, ส่ง periodic ออกทุก interface ไปที่ reserved multicast MAC และ ไม่ถูก forward ต่อ (link-local)
  • enable by default ทุก interface; ตั้งได้ทั้ง system level และ interface level — ถ้า system disable = ปิดทุก interface แม้ interface enable
  • configurable แค่ admin-state, hello-timer (default 30s), hold-multiplier (default 4)
  • ค่าที่ส่ง: chassis MAC (chassis-id type = MAC เท่านั้น), interface name (port-id), system capabilities, system name (= hostname), system description (SW version + hostname + kernel)
  • ใช้ทำ topology discovery / troubleshoot / automation — ไม่ใช่กลไกตรวจ link fail เร็ว (นั่นคือหน้าที่ของ BFD)
  • ดู: show system lldp neighbor, info from state system lldp

LAG

  • IEEE 802.1AX, รวม link เพื่อเพิ่ม BW + availability
  • hashing ทำให้ flow เดียวกันวิ่ง link เดียว (ไม่ reorder); member ต่าง speed ได้
  • สูงสุด 128 LAG/เครื่อง (ขึ้นกับ HW: 7220-D = 32, H = 127, IXR-6/10 = 128), 64 member/LAG
  • สร้าง 2 ขั้น:
    1. interface lagN + lag { } (subinterface สร้างบน lag) — lag-type default = static
    2. member: interface ethernet-1/3 ethernet aggregate-id lag100 (member ไม่มี subinterface)
  • min-links default 1; static LAG up ทันทีที่มี member up 1 ตัว
  • static LAG ตรวจ miscabling ไม่ได้
  • LACP ส่ง control frame ทุก member และระบุ far-end node (system-id-mac, default = chassis MAC) กับ LAG (admin-key 1..65535) → block member ที่ต่อไปผิด node หรือผิด LAG (oper-down-reason other, OUT_SYNC)
  • LACP params:
    • interval SLOW = 30s / FAST = 1s
    • lacp-mode ACTIVE (ส่ง+ตอบ) / PASSIVE (ตอบอย่างเดียว)
    • system-priority (ฝั่งไหนตัดสิน active link)
    • ต้องเปิดทั้งสองฝั่ง; active-standby LAG ยังไม่รองรับ
  • micro-BFD สำหรับ LAG: รัน BFD ทุก member, ต้องระบุ local/remote IP
    • desired-minimum-transmit-interval, required-minimum-receive (หน่วย microseconds, 10000..100000000), detection-multiplier (default 3)
    • interval ที่ใช้จริง = ค่าที่สูงกว่า ระหว่าง desired-tx ของเรากับ required-rx ของอีกฝั่ง (เช่น 100ms × 3 = ตรวจเจอใน 300ms)
A:dc-leaf-2# info interface lag100
    lag {
        lacp {
            interval SLOW
            lacp-mode ACTIVE
            admin-key 32768
            system-id-mac 1A:E9:07:FF:00:00
            system-priority 100
        }
    }
A:dc-leaf-2# show lag lag100 lacp-state

เทียบ SR OS: SR OS port ≈ SR Linux interface (L2), SR OS router interface/SAP ≈ SR Linux subinterface; SR Linux ไม่มี system interface แบบ SR OS ใน base router แต่มี system0 ใช้เป็น VTEP; LAG ของ SR OS ใช้ lag N port ... + mode access/network, LACP param คล้ายกัน

2.3 Network Instances, IP-VRF, MAC-VRF, IRB

สาระสำคัญ

  • network-instance = VRF (คำจาก OpenConfig) มีชื่อ, type, subinterfaces, routing/forwarding table, protocol instance (BGP/OSPF/IS-IS) และ static routes ของตัวเอง; แต่ละอันคือ Linux network namespace
  • type มี 3 แบบ:
    • default — มีได้ อันเดียว ต้องชื่อ "default" = base routing instance / GRT
    • ไม่ถูกสร้างอัตโนมัติ ต้องสร้างเอง
    • เป็น อันเดียวที่ใช้ resolve next-hop ของ tunnel (VXLAN)
    • ip-vrf — L3, forward ตาม destination IP, มี route table ของตัวเอง; ใส่ routed subinterface
    • mac-vrf — L2 broadcast domain, forward ตาม destination MAC ด้วย bridge table (MAC table)
    • ใส่ bridged subinterface + IRB ได้แค่ 1 อัน
    • protocols/static-routes ใช้ไม่ได้
    • รองรับบน 7220 IXR family
  • subinterface ต้องผูกกับ network-instance ถึงจะ forward ได้; 1 subinterface อยู่ได้ 1 network-instance; 1 NI มีได้หลาย subinterface
  • mgmt network-instance: ถูกสร้างจาก factory config
    • type ip-vrf, มี mgmt0.0 (DHCP client v4+v6), SSH เปิดบน NI mgmt
    • เพิ่ม interface อื่นเพื่อทำ in-band mgmt ได้
  • ping/traceroute ต้องรู้ NI:
    • ระบุ network-instance X หรือใช้ NI ของ context ปัจจุบัน
    • ถ้าไม่ได้อยู่ใน context ของ NI ใด จะใช้ mgmt โดย default
    • IPv6 ใช้ ping6/traceroute6
  • Route table: show network-instance default route-table [all|ipv4-unicast|ipv6-unicast|next-hop|summary]
    • Owner: local, host, static, bgp, ospf, isis, aggregate…; ID 0 = active
    • Next-hop type: extract (ส่งขึ้น CPM), direct (local interface), indirect (non-local), discard, reject (drop + ICMP unreachable), tunnel
    • Active route = มีใน FIB; inactive เพราะมีตัวที่ดีกว่า หรือ next-hop unresolved
  • Route selection:
    • protocol ต่างกัน → preference ต่ำชนะ (= admin distance)
    • protocol เดียวกัน preference เท่ากัน → metric ต่ำชนะ
    • เท่ากันหมด → ECMP (สูงสุด 64 next-hop, static ได้ 128)

MAC-VRF & IRB

  • ไม่มี mac-vrf: 1 server = 1 subnet → route table ใหญ่; มี mac-vrf: หลาย server อยู่ subnet เดียว, IRB เป็น gateway
  • IRB = internal L3 interface irb<0..255> (สูงสุด 256) เชื่อม mac-vrf ↔ ip-vrf
    • subinterface ของ IRB ต้อง routed, ไม่มี VLAN
    • mtu/vlan-tagging/transceiver/ethernet ใช้ไม่ได้, ตั้ง IP-MTU ได้
    • IRB subinterface ต้องใส่ทั้งใน mac-vrf และ ip-vrf/default
  • mac-vrf มี IRB ได้ 1, ip-vrf มีได้หลาย IRB (แต่ละอันไป mac-vrf คนละตัว) → IRB ไม่ได้ใช้เชื่อม ip-vrf กับ ip-vrf
  • bridged subinterface: ไม่มี IP/ip-mtu; มี bridge-table (discard-unknown-src-mac, mac-learning, mac-duplication, mac-limit)

สรุปที่ควรจำ — MAC table

  • learn source MAC / flood unknown dest; type: irb-interface, learnt, static, duplicate
  • aging default 300 วินาที; IRB/static ไม่ age
  • static MAC: destination = subinterface หรือ blackhole
  • mac-limit default 250 entries (range 1..8192) ต่อ mac-vrf และ default 250 ต่อ subinterface; warning threshold 95% (clear ที่ threshold − 5%)
  • mac-learning / aging ปิดได้ทั้งระดับ mac-vrf และ subinterface; ปิด learning → flood ทุกอย่าง
  • discard-unknown-dest-mac (ระดับ mac-vrf) = ไม่ flood unknown dest
  • discard-unknown-src-mac (ระดับ subinterface) = anti-spoof (รับเฉพาะ source ที่อยู่ใน table/static)
  • MAC duplication (MAC move) = กลไกกัน L2 loop — enable by default
    • อาการ: MAC เดียวกันถูก re-learn สลับ interface เร็ว ๆ (duplicate MAC จริง, switch กลาง flood, cable loop)
    • monitoring-window 3 นาที, num-moves 5, hold-down-time 9 นาที, action stop-learning (default)
    • ตั้งที่ mac-vrf, override ได้ที่ subinterface (use-net-instance-action = default)
    • action ทำกับ subinterface ที่ learn MAC แล้วทำให้เกิน threshold; อยู่จน hold-down หมด
    • show output ตัวอย่างอาจแสดง "Number of moves allowed: 4" ทั้งที่ config num-moves 5 — เพราะ move ครั้งที่ 5 คือครั้งที่เกิน threshold
    • [ตั้งแต่ 26.3] เอกสาร 26.3 แสดง default hold-down-time 10 (รุ่นที่อธิบายข้างต้นคือ 9 นาที) — ควรตรวจค่าจริงบนเครื่องที่ใช้

2.4 Static Routes, Next-Hop-Group, ECMP

สาระสำคัญ

  • static route 2 ขั้น:
    1. static-routes route <prefix> → prefix + preference + metric + admin-state + อ้าง next-hop-group
    2. next-hop-groups group <name> → list ของ next-hop (IP) หรือ blackhole (drop) — หลาย route ใช้ NHG เดียวกันได้ (แก้ next-hop ที่เดียว)
  • NHG: next-hop ต้องเป็น IPv4 ทั้งหมดหรือ IPv6 ทั้งหมด (ห้ามผสม); สูงสุด 128 next-hop ต่อ group
  • ข้อดี static: config ง่าย (เครือข่ายเล็ก), CPU ต่ำ, ไม่มี protocol overhead, predictable
  • ข้อเสีย: ไม่ scale

สรุปที่ควรจำ — defaults

Parameter อยู่ที่ Default
admin-state route / NHG / nexthop enable
metric static-routes route 1
preference static-routes route 5
blackhole next-hop-group (exclusive กับ nexthop list) —
generate-icmp NHG blackhole false
resolve NHG nexthop true (false = ต้อง resolve ด้วย local route เท่านั้น)
  • resolve true = recursive lookup ผ่าน route อะไรก็ได้ (BGP/IGP/static) เช่น next-hop = loopback ของ spine ที่เรียนจาก BGP
  • route จะถูก install ถ้า: admin enable + next-hop reachable อย่างน้อย 1 + preference ต่ำสุด + (pref เท่ากัน) metric ต่ำสุด
  • ไม่มี routing policy ผูกกับ next-hop ใน NHG
network-instance default {
    static-routes {
        route 192.168.20.0/30 {
            next-hop-group NHG-leaf-2
        }
    }
    next-hop-groups {
        group NHG-leaf-2 {
            nexthop 1 { ip-address 10.1.1.0 }
            nexthop 2 { ip-address 10.2.1.0 }
        }
    }
}
  • ตัวอย่างนี้มี 2 next-hop = ECMP
  • [ตั้งแต่ 26.3] มี static route 2 แบบ:
    • Legacy model (network-instance static-routes + next-hop-groups) — แบบที่อธิบายในหัวข้อนี้
    • New model (network-instance static, OpenConfig-based) — next-hop แยก index และใส่ tunnel encap ได้

สรุปที่ควรจำ — ECMP

  • ECMP enable by default สำหรับ static และ routing protocol (แต่ BGP multipath default = 1 path ต้องเพิ่มเอง — ดู 2.5)
  • เลือก next-hop ด้วย hash (src/dst IP, src/dst port, protocol, ipv6-flow-label, vlan, mpls label + hash-seed) → hash % N (N = จำนวน next-hop)
    • flow เดียวกันไป path เดียวกัน (ไม่ reorder)
    • ไม่ใช่ round-robin
  • system load-balancing hash-options <destination-address|source-address|destination-port|source-port|protocol|vlan|ipv6-flow-label|mpls-label-stack|hash-seed>
  • Polarization: ถ้า hash จากเนื้อ packet อย่างเดียว ทุก router ได้ผลเท่ากัน → multi-stage ECMP บาง link ว่าง
    • แก้ด้วย hash-seed ต่างกันทุก router (default hash-seed สร้างจาก system MAC)
  • Resilient hashing: bucket คงที่ — เมื่อ next-hop หายไป เฉพาะ flow ที่ใช้ next-hop นั้นถูกย้าย (modulo ปกติทำให้ flow อื่นขยับด้วย); route table แสดง "Resilient hash routes"
flowchart LR
  P["packet: src/dst IP, src/dst port, proto"] --> H["hash()"]
  S["hash-seed ต่อ router (default จาก system MAC)"] --> H
  H --> M["hash % N"] --> NH["next-hop #k (flow เดียวกัน = path เดิม)"]

เทียบ SR OS: SR OS ใส่ next-hop/blackhole ที่ static-routes route X route-type unicast เลย; SR Linux แยก NHG; SR OS ECMP ต้องตั้ง ecmp N ใน router (default 1) — SR Linux static ECMP ใช้ได้ทันทีถ้า NHG มีหลาย next-hop

2.5 BGP underlay, Routing Policy, BFD

สาระสำคัญ

  • SR Linux ใช้ protocol stack จาก SR OS; แต่ละ network-instance รัน IS-IS/OSPF/BGP ได้ แต่หัวข้อนี้เน้น BGP
  • ฟีเจอร์ BGP:
    • iBGP + eBGP, IPv4 + IPv6, import/export policy
    • ECMP สูงสุด 64 next-hop, MD5 auth, BFD, route reflector
    • dynamic neighbors (รับ session ที่ peer เริ่ม)
  • BGP พื้นฐาน: RFC 4271, Internet routing protocol, MP-BGP (IPv6, L2VPN/EVPN, L3VPN, flowspec)
    • AS = กลุ่ม router ภายใต้การจัดการเดียวกัน ระบุด้วย ASN
    • หน้าที่ของ BGP: (1) advertise prefix ข้าม AS + เลือก best (2) policy ว่าจะรับ/ส่งอะไร
  • AS-path: eBGP prepend ASN ตัวเองทุกครั้งที่ส่งออก (iBGP ไม่เปลี่ยน)
    • ใช้ (1) เลือก path สั้นสุด (2) loop detection (เห็น ASN ตัวเองใน path = ทิ้ง)
    • iBGP ไม่ re-advertise route จาก iBGP peer → ต้อง full mesh หรือ RR
  • DC design:
    • spine ทั้งหมด AS เดียวกัน (64999), leaf แต่ละตัว AS ของตัวเอง (65001…)
    • private ASN 64512–65534 (หรือ 4-byte)
    • eBGP ทุก leaf↔spine
    • leaf advertise subnet ของ server ตัวเอง → spine ส่งต่อให้ leaf อื่น
    • ถ้า leaf ส่งกลับไป spine อื่น spine จะเจอ AS loop (เห็น 64999) แล้วทิ้ง → optimization: export เฉพาะ local prefix
  • Leaf ไม่ได้ peer กับ leaf อื่นโดยตรง — เรียนผ่าน spine
  • Guidelines:
    • eBGP leaf-spine
    • export policy (ประกาศ server subnet), import policy (รับจาก spine)
    • เปิด ECMP + BGP multipath

Routing policy

  • อยู่ใต้ routing-policy (top-level) ประกอบด้วย:
    • prefix-set (IPv4+IPv6 ปนได้, mask-length-range exact หรือ 24..26)
    • community-set (ค่าตรง/regex/well-known), as-path-set (regex), extended-community-set, tag-set
    • policy
  • policy = default-action + statement เรียงเลข
    • first match ชนะ; ไม่ match → default-action
    • หลาย match condition ใน statement เดียว = AND
  • match: protocol, family (ipv4/ipv6/evpn/route-target), prefix-set, bgp community-set / as-path-set / as-path-length
  • action: policy-result accept | reject | next-policy | next-statement + แก้ BGP attr (as-path prepend/remove/replace, communities add/remove/replace, local-preference, origin, med)
  • apply: import-policy / export-policy ที่ global/group/neighbor (เจาะจงสุดชนะ) — policy ที่ apply แล้วจะ override ebgp-default-policy
  • Well-known community:
    • no-export (ห้ามส่งต่อให้ eBGP peer, iBGP ได้)
    • no-advertise (ห้ามส่งให้ใครเลย)
  • ตัวอย่าง import: set local-preference 150 ให้ route จาก spine-1 → Loc-RIB เลือก path จาก spine-1 อันเดียว (ECMP หาย, tie-break = local-pref)
  • ตัวอย่าง export: prepend ASN ตัวเอง 3 ครั้ง (as-number auto repeat-n 3) + add community → ให้ peer ไม่ชอบ path นี้
  • Generic policy best practice:
    • default accept, reject /31 (0.0.0.0/0 mask-length-range 31..31), reject as-path-length ≥ 1 (route ที่เรียนจากคนอื่น)
    • เหลือแค่ local loopback + host subnet
    • ใช้ policy เดียวกันทุก leaf

2.6 EVPN-VXLAN: L2 และ L3

สาระสำคัญ — Underlay/Overlay & VXLAN

  • Underlay = IP fabric (ปกติ eBGP ตาม RFC 7938); Overlay = VPN ผ่าน tunnel ระหว่าง endpoint, แลก reachability ด้วย iBGP (EVPN)
  • VXLAN (RFC 7348) = L2 over IP/UDP (MAC-in-UDP); VTEP = จุด encap/decap อยู่บน hypervisor, leaf, หรือ DCGW; VNI ระบุ VXLAN segment/tunnel
  • Packet format: Outer Ethernet (14B) + Outer IP (20B) + UDP (8B, dst port 4789) + VXLAN header (8B, VNI 24 bit ≈ 16M segment) + inner Ethernet frame
    • UDP source port = hash จาก inner flow → ECMP ใน underlay กระจายได้
    • outer src IP = ingress VTEP, outer dst IP = egress VTEP; outer Ethernet เปลี่ยนทุก hop
    • overhead ~50 byte → ต้องเผื่อ MTU underlay

สาระสำคัญ — EVPN

  • EVPN = address family ของ MP-BGP: AFI 25 (L2VPN) / SAFI 70 (EVPN); ทำ auto-discovery VTEP + เรียน/กระจาย MAC/IP ใน control plane → ไม่มี flood-and-learn ข้าม fabric; RFC 8365 (NVO), RFC 7432 (route types)
  • next-hop ใน MP_REACH_NLRI = IP ของ VTEP (system0)
  • spine มักทำ RR (ต่อกับทุกตัว, ไม่มี VTEP workload)

สรุปที่ควรจำ — EVPN route types

Type ชื่อ ใช้ทำอะไร ใช้ใน
RT1 Ethernet Auto-Discovery (A-D) multi-homing: aliasing + mass withdraw (fast convergence); มี per-ES และ per-EVI MH
RT2 MAC/IP Advertisement ประกาศ MAC (หรือ MAC+IP) ของ host/IRB → สร้าง bridge table (+ARP/ND) L2, asymmetric L3
RT3 Inclusive Multicast Ethernet Tag (IMET) discover VTEP ใน service เดียวกัน + สร้าง flooding list สำหรับ BUM L2 (ทุก mac-vrf ที่มี vxlan)
RT4 Ethernet Segment (ES) MH: discover leaf ใน ES เดียวกัน + DF election MH
RT5 IP-Prefix ประกาศ IP prefix (inter-subnet, L3) แยกจาก MAC symmetric L3

L2 EVPN operation

  • BD = instance ของ EVPN L2 service บน VTEP หนึ่ง; EVI = กลุ่ม BD ที่เป็น service เดียวกันข้ามหลาย VTEP — แต่ละ EVI มี RD และ RT
  • single-homed host → VTEP ส่งแค่ RT2 + RT3
  • Local MAC learning ด้วย data plane เฉพาะ local interface → ประกาศเป็น RT2 (MAC, RD, label = VNI, RT) → VTEP อื่นเช็ก RT ตรงกับ import-rt → ติดตั้ง MAC ชี้ไป "tunnel to VTEP1 (VNI)"; remote MAC เป็น type evpn ใน mac table
  • RD = แยก route ของต่าง EVI (overlap ได้), auto = system0-IP:EVI; RT = ตัดสินว่า route ไหน import เข้า NI ไหน, auto = local-AS:EVI (แต่ใน DC leaf ASN ต่างกัน → ต้องตั้ง RT เองให้เหมือนกันทุก VTEP)
  • MP-BGP instance เดียวส่ง route ของทุก EVI
  • IMET (RT3) มี: RD ของ mac-vrf ผู้ส่ง, Originating router IP (VTEP IP), RT, tunnel type = ingress replication, tunnel ID/label = VNI (+ community bgp-tunnel-encap:VXLAN) → ผู้รับเอาไปสร้าง flooding list (flooding list ไม่ได้อยู่ใน route — เป็นผลลัพธ์ที่ผู้รับสร้าง)
  • BUM: VTEP ดู flooding list ของ EVI แล้ว ingress replication ส่งสำเนาไป VTEP ทุกตัวใน list

Multi-homing

  • ES (Ethernet Segment) = ชุด link ที่ต่อ host ไปยัง leaf ≥1 ตัว; ESI (10 byte) = unique ทั้ง network (global), ทุก leaf ใน ES เดียวกันใช้ ESI เดียวกัน; ESI 0 = single-homed, 0xFF = MAX-ESI (reserved)
  • RT1 (A-D per-ES: หาว่า leaf ไหนอยู่ ES ไหน; A-D per-EVI: ผูก ES กับ EVI) + RT4 (ES discovery + DF election)
  • โหมด: single-active (leaf เดียว forward) / all-active (ทุก leaf forward, host ต้องใช้ LAG กัน BUM ซ้ำ/loop) — SR Linux (VXLAN) รองรับเฉพาะ all-active, สูงสุด 4 peer

L2 EVPN config workflow: (1) system0.0 (2) BGP EVPN peering (3) local bridged interfaces (4) vxlan-interface (5) mac-vrf + bgp-evpn/bgp-vpn

  • system0: virtual, always up, ต้องอยู่ใน network-instance default, มี subinterface เดียว 1 IP (v4/v6); source IP ของทุก VXLAN tunnel (เปลี่ยนไม่ได้), ใช้ auto-derive RD, เป็น default source ของ multihop BGP (เปลี่ยนได้ด้วย transport local-address); ต้อง export system0 /32 เข้า underlay ด้วย
  • EVPN BGP peering: อยู่ใน network-instance default แต่เป็น group แยกจาก underlay, ปกติ iBGP — ทุก VTEP + RR อยู่ AS เดียวกัน (เช่น 65000) ที่ต่างจาก underlay (ใช้ local-as), เปิด afi-safi evpn, ปิด ipv4-unicast ใน group นั้น; full mesh หรือ RR (บน spine หรือ VNF); RR ใช้กับ EVPN ได้ปกติ

3.1 Logging

สาระสำคัญ

  • SR Linux logging สร้างบน Linux rsyslog (rsyslogd) — รองรับทั้ง local และ remote; ข้อความ syslog มี อย่างน้อย time, hostname, application name, message; ส่ง remote ได้ทั้ง UDP และ TCP
  • config จาก CLI/gNMI/JSON-RPC ถูก แปลงเป็น /etc/rsyslog.conf (แก้ไฟล์ตรงได้แต่จะถูก overwrite เมื่อแก้ผ่าน CLI)
  • ไฟล์ Linux: /var/log/messages (default ของ CentOS/RedHat; SR Linux app log ก็ลงที่นี่ด้วย), /var/log/secure (auth/SSH), /var/log/srlinux/ (log ที่ config ใน SR Linux), /var/log/ztp (ZTP)
  • ไม่มี "encrypted local file" — rsyslog เข้ารหัสได้แค่ตอนส่ง remote ด้วย TLS

สรุปที่ควรจำ — Logging = Source → (filter) → Destination

ตัวเลือก
Destinations (4) file (persistent, default dir /var/log/srlinux/file), buffer (RAM/tmpfs /var/log/srlinux/buffer, หายตอน reboot, ทำ persist ได้), console (/dev/console = serial port, ไม่เก็บ), remote-server (UDP/TCP, default port 514, ต้องระบุ network-instance ที่ใช้ route ไป)
Sources (3) facility + priority (Linux native: kern, auth, cron, daemon, local0–7 …), subsystem + priority (SR Linux app: aaa, accounting, acl, bgp, chassis, lldp, netinst, …), filter (syslog filter ที่สร้างไว้)
ไม่ใช่ source console (console เป็น destination เท่านั้น)
- SR Linux app ทั้งหมดถูก report เป็น Linux facility local6
- Priority (severity) 0–7: 0 emergency, 1 alert, 2 critical, 3 error, 4 warning, 5 notice, 6 informational, 7 debug (0 = รุนแรงสุด); match-above X (X และรุนแรงกว่า) vs match-exact X
- filter (system logging filter <name>): match ด้วย contains, prefix, regex, tag (เช่น sr_bgp_mgr, chassis), facility+priority; หลายเงื่อนไขใน filter = AND; แล้วอ้างใน destination filter [ name ]
- file params: directory (default /var/log/srlinux/file), format (RSYSLOG_FileFormat), rotate default 4, size default 10M; หลาย subsystem/facility/filter ใน destination เดียว = log ทุกอันที่ match (OR)
- ใช้ severity เพื่อลดปริมาณ log ให้เหลือเฉพาะที่สำคัญ

สรุปที่ควรจำ — Default logging config (3 destination)

ชื่อ ชนิด source
buffer messages buffer local6 (SR Linux) match-above informational (ทุกอย่างยกเว้น debug)
buffer system buffer Linux facility อื่นทั้งหมด (ไม่รวม local6) match-above warning
file messages file local6 match-above warning (log สำคัญของ SR Linux เก็บถาวร)

Show / debug

  • show system logging = list ของ file/buffer; show system logging file <name> / show system logging buffer <name> (pipe | grep, | tail --lines N ได้)
  • debug = priority ระดับ 7 ใช้คู่กับ trace-options ของแต่ละ app (BGP: trace-options flag packets/keepalive/... modifier detail) — ต้องมี ทั้ง trace-options + destination ที่รับ priority debug ถึงจะเห็น
  • trace-options มีใน: system LLDP, interface DHCP, BGP (global/group/neighbor), IS-IS, gNMI server, JSON-RPC server
  • ทดสอบด้วย bash logger -p mail.error "msg" (format facility.priority)

3.2 ACLs, CPM-filter, Policers, Capture-filter

สาระสำคัญ — ชนิด ACL และลำดับการประเมิน

ACL ติดตั้งที่ไหน / ทิศทาง ทำอะไร จำนวน
System ACL ทุก line card, ทุก interface, ingress — ก่อนทุกอย่าง (ก่อน tunnel termination) accept/drop/log; ตัวเดียวที่ match outer header ของ VXLAN ที่ terminate บนตัวเอง (7220 IXR-D เท่านั้น) 1 IPv4 + 1 IPv6 (ชื่อ system)
Ingress (input) ACL subinterface เฉพาะ, line card นั้น accept/drop/log หลายอัน
Capture ACL ทุก line card, ทุก subinterface ingress รวม mgmt copy packet ขึ้น CPM ให้ traffic-monitor (tcpdump-like) 1 IPv4 + 1 IPv6 (ชื่อ capture)
CPM ACL (cpm-filter) ทุก line card (เมื่อ apply ที่ control plane), เฉพาะ traffic ที่ terminate บน CPM รวม OOB mgmt control-plane protection / กัน DoS: accept/drop, rate-limit ด้วย policer 1 IPv4 + 1 IPv6 (ชื่อ cpm)
Egress (output) ACL subinterface, ขาออก accept/drop (7220-D: egress ไม่มี log) หลายอัน
- ลำดับ: 1) System → 2) Ingress → 3) Capture → 4) CPM → 5) Egress; ถ้า ingress ACL drop control traffic ไปแล้ว cpm-filter ไม่เห็น
- (คำว่า ACL กับ filter ใช้แทนกันได้: cpm-filter = CPM ACL, capture-filter = capture ACL)

สรุปที่ควรจำ — กฎ ACL

  • acl acl-filter <name> type ipv4|ipv6|mac → entry sequence 1..65535, เลขต่ำประเมินก่อน, first match ชนะ, ไม่ใส่ match = match all; หลาย criteria ใน entry = AND
  • default action = accept เสมอ → ถ้าต้องการ default drop ใส่ entry สุดท้าย (เช่น 65535) match-all + drop
  • match: L3 (src/dst IP/prefix, protocol/next-header, dscp, fragment, ICMP type/code), L4 (src/dst port เป็นชื่อหรือเลข, range, tcp-flags)
  • action: accept (+ rate-limit policer/system-cpu-policer ใน cpm), drop, copy (capture), log; statistics-per-entry true = นับ hit
  • 7220 IXR-D: ingress ไม่รองรับ log กับ accept, egress ไม่รองรับ log เลย; cpm-filter log ได้เฉพาะ drop
  • apply interface ACL:
A:leaf1# acl interface ethernet-1/10.0 input acl-filter block-v4-infrastructure type ipv4

หมายเหตุ: ตั้งแต่ 25.3 ไวยากรณ์อยู่ใต้ acl interface <subif> input|output

  • TCAM: ACL อยู่ใน TCAM บน line card เพื่อ line rate; default subinterface-specific disabled = หลาย subinterface ใช้ TCAM entry ร่วม (stats รวม); input-only | output-only | input-and-output = แยก entry/สถิติต่อ subinterface; commit ACL ถูกเช็กว่า TCAM พอทุก line card ไม่พอ = commit fail; threshold platform acl/tcam resource ... rising-threshold-log / falling-threshold-log (default 90/70%), show platform linecard 1 detail, show resource-monitoring
  • show/clear: show acl summary, show acl acl-filter X type ipv4 [subinterface Y entry 10], tools acl acl-filter X type ipv4 statistics clear; system ACL ไม่มี show ใช้ info from state acl-filter system type ipv4

สรุปที่ควรจำ — CPM-filter

  • apply: system control-plane-traffic input acl acl-filter cpm type ipv4 — แนะนำ commit now confirmed timeout 120 กันตัวเองหลุด
  • best practice: อนุญาตเฉพาะ protocol + source ที่ต้องใช้ (BGP จาก peer, SSH จาก mgmt subnet, BFD …) แล้ว entry 65535 drop + log; ดู log ด้วย destination ที่มี subsystem acl
  • Hierarchical policing (กัน line card เดียวทำ CPU อดอยาก):
    • policer (distributed) = ต่อ line card, hardware, หน่วย peak-rate-kbps + maximum-burst-size (bytes)
    • system-cpu-policer = บน CPM, software, รวม traffic จากทุก line card, หน่วย peak-rate-pps + maximum-burst-packet
    • bucket ถูก "ระบาย" ที่ peak-rate; ถ้าเต็มถึง max-burst → non-conforming = drop
    • entry ใช้ได้ไม่มี / policer อย่างเดียว / system-cpu อย่างเดียว / ทั้งคู่; entry-specific default false (หลาย entry แชร์ rate เดียว), true = instance ต่อ entry
    • เฉพาะ cpm-filter เท่านั้นที่ rate-limit ได้ (interface/capture ACL ไม่มี policer)
acl acl-filter cpm type ipv4 {
    entry 10 { match { ipv4 { protocol tcp source-ip { prefix 10.2.1.0/32 } } transport { destination-port { value 179 } } } action { accept { } } }
    entry 20 { match { ipv4 { protocol tcp source-ip { prefix 172.18.18.0/24 } } transport { destination-port { value ssh } } } action { accept { } } }
    entry 100 { match { ipv4 { protocol icmp } } action { accept { rate-limit { system-cpu-policer pol-1 policer pol-1 } } } }
    entry 65535 { action { log true drop { } } }
}
acl policers {
    system-cpu-policer pol-1 { entry-specific true peak-rate-pps 5000 maximum-burst-packet 500 }
    policer pol-1 { entry-specific true peak-rate-kbps 1000 maximum-burst-size 1000 }
}

สรุปที่ควรจำ — Capture-filter + traffic-monitor

  • capture-filter: 1 IPv4 + 1 IPv6, ติดทุก subinterface ingress (รวม mgmt0.0), action copy → CPM; ไม่ drop, ไม่มี policer
  • tools system traffic-monitor [hexdump] [verbose] [output-file X.pcap] [protocol|source-address|destination-address|source-port|destination-port ...]
    • ต้องมี capture-filter อยู่ หรือใส่ match criteria → สร้าง capture-filter on the fly (entry เดียว, ไม่มี range, ทีละ user, overwrite ของเดิมถ้ายืนยัน warning)
    • SR Linux เติม header 48 byte หน้า packet ที่ copy (มี ingress interface) → ต้องตัดออก (editcap) ก่อนเปิด pcap ใน Wireshark
    • หลาย user ดู traffic-monitor พร้อมกันได้ (ถ้าไม่ได้สร้าง filter ใหม่)
  • System ACL vs subinterface ACL กับ VXLAN: บน VTEP, packet VXLAN ที่ terminate จะถูก decap ก่อนถึง subinterface ACL → subinterface/CPM/capture ACL เห็นแค่ inner; ต้องใช้ system ACL match UDP 4789 outer; ถ้าแค่ transit ทั้งสองแบบเห็น outer

ตัวอย่างการใช้งาน: ACL leaf-spine/block-v4-infrastructure match destination 10.0.0.0/8 drop → apply input บน subinterface ฝั่ง host (เช่น ethernet-1/10.x) เพื่อกัน host เข้าถึง IP infra

เทียบ SR OS: SR OS ip-filter ผูก SAP/interface ingress/egress ≈ subinterface ACL; CPM filter (system security cpm-filter) ≈ cpm-filter (SR OS มี cpu-protection policer แยก); default action ของ SR OS ip-filter = drop (ตั้งได้) แต่ SR Linux default = accept; capture ≈ SR OS mirror + debug ... packet ไม่มีเครื่องมือ tcpdump ในตัวแบบนี้

4. User and System Management

4.1 Users, AAA, roles

สาระสำคัญ

  • User 3 แบบ:
    1. SR Linux users (local, นิยามแยกจาก Linux, UID ≥ 1500) — default admin (full access)
    2. Linux users (UID 1000–1499) — เข้าถึงไฟล์/process ของ SR Linux ได้; ไม่แนะนำให้สร้าง; มี linuxadmin / password linuxadmin โดย default จึงควรเปลี่ยน
    3. Remote users (TACACS+) — ได้ random UID ตอน login ครั้งแรก (คงเดิมทุก session) และระบบสร้าง home dir ให้ - ไม่มี "container users"
  • Authentication ทั้งหมดผ่าน Linux PAM
    • aaa_mgr ใช้ PAM จัดการ auth ให้ทุก app
    • ทุกการเข้าถึงต้องผ่าน aaa_mgr: console, SSH, FTP, gNMI/gRPC, JSON-RPC, SNMP
  • Accounting = บันทึก คำสั่งที่ user สั่ง → เก็บ local file หรือส่ง TACACS+ server-group
  • TACACS+ server-group: หลาย server, ลองแบบ round-robin
    • params: name, network-instance, IP, port, secret key
  • Roles: rule ต่อ path ของ CLI tree + action read / write / deny มี 3 ขั้น:
    1. สร้าง role ที่ system aaa authorization role <name>
    2. ใส่ rule ที่ system configuration role <name> rule <path> action <read|write|deny>
    3. สร้าง user ที่ system aaa authentication user <name> password .. role [..] - user ที่ไม่มีสิทธิ์จะได้ Error: No authorization to execute command
  • CPM filter บล็อกตาม source IP/protocol ได้ แต่ไม่ได้ "บล็อก unauthorized user" — การยืนยันตัวตน user เป็นงานของ AAA

A:dc-leaf-1# system configuration role user-role rule / action write
A:dc-leaf-1# system configuration role user-role rule /acl action read
A:dc-leaf-1# system aaa authentication user bob-user password 123aad role [ user-role ]
A:leaf1# system aaa accounting accounting-method [ local ]
A:leaf1# system aaa accounting event command record stop
A:leaf1# system logging file accounting rotate 4 size 10M subsystem accounting

เทียบ SR OS: SR OS ใช้ system security user + profile (entry match command → permit/deny) + user-template สำหรับ TACACS+/RADIUS; SR Linux role ≈ profile ของ SR OS แต่อิง YANG path; SR OS ไม่มีแนวคิด "Linux user"

4.2 TLS, PKI, gNMI/JSON-RPC server

สาระสำคัญ

  • gNMI/gRPC และ JSON-RPC ควรใช้ TLS profile เพื่อความปลอดภัย
    • SR Linux เป็น server, client = app ที่ส่ง gNMI/JSON request
  • PKI = ระบบจัดการ certificate ของ public-key system สำหรับ encryption + authentication
    • CA = trusted third party รับรองตัวตนของ subject
  • asymmetric (public/private key) ใช้ทรัพยากรสูง จึงใช้แลก session key แล้วใช้ symmetric encryption คุยกันจริง
    • TLS handshake ต่อรอง cipher + แลก key
  • Certificate (X.509, ส่วนมาก format PEM) มี identity (CN, org) + public key ของ subject — ไม่มี private key เด็ดขาด
  • Flow:
    1. client/server สร้าง key pair เอง
    2. ส่ง CSR ไป CA
    3. CA เซ็น cert ด้วย private key ของ CA
    4. client ขอเชื่อม
    5. server ส่ง cert (+ขอ cert client)
    6. client ตรวจ cert ด้วย public key ของ CA แล้วส่ง cert ตัวเอง
    7. server ตรวจ cert client
  • CA ไม่ได้สร้าง key pair ให้ subject (subject สร้างเอง)

4.3 Zero Touch Provisioning

สาระสำคัญ

  • ZTP = ทำให้ router ทำงานในเครือข่ายได้โดยไม่ต้อง pre-provision
    • จัดการโดย ZTP application ซึ่งเป็นส่วนของ autoboot และรันเป็น Linux OS service ก่อน SR Linux จะ start
    • ได้ boot parameter จาก DHCP และดาวน์โหลด Python provisioning script

สรุปที่ควรจำ — ZTP process

  1. Linux ตรวจ autoboot flag ใน grub.cfg
    • สั่งซื้อด้วย part number ที่ถูก = autoboot enable มาเลย
    • autoboot ทำผ่าน mgmt port เท่านั้น (ตามเอกสารรุ่นพื้นฐาน)
  2. ส่ง DHCP request (ได้ IP, mask, gateway, NTP, URL)
  3. DHCP option 66 + 67 หรือ option 43 บอกที่อยู่ provisioning script (HTTP/HTTPS/FTP URL)
  4. ดาวน์โหลดและรัน script
  5. ZTP start app_mgr → app_mgr start app อื่น
  • ทุก event ถูก log (console + /var/log/ztp)
  • สำเร็จ → ลบ autoboot flag ใน grub.cfg (reboot ครั้งหน้าจะไม่ ZTP ซ้ำ)
  • fail/timeout → restart ZTP (retry default 3) → เกินแล้ว reboot → วนจนสำเร็จหรือมีคนเข้าไปแก้ (เช่นลบ flag)
  • server ที่ต้องมี: DHCP server (+ DHCP relay ถ้าต่าง subnet) และ HTTP/FTP file server (script, RPM, image) อยู่คนละ subnet ได้
  • ZTP CLI ใช้ได้ก่อน SR Linux start: ดู status, start/stop/restart ZTP, จัดการไฟล์/image, แก้ timer/retry/grub.cfg — ไม่จำเป็นต่อ autoboot
  • สาเหตุที่ ZTP ล้มเหลว:
    • DHCP ไม่ตอบ (server/relay เสีย)
    • offer ไม่มี option 66/67/43
    • login/download script ไม่ได้
    • copy script/RPM/image ลง storage ไม่ได้
    • script return error
  • ZTP แบบพื้นฐานนี้ ไม่มีขั้นตอน CSR/certificate และ ไม่ใช้ PKI; FSS/EDA ไม่ใช่ ส่วนของ autoboot

5.2 EDA use cases: intent automation, transactions, deviations, observability

สาระสำคัญ

  • Fabric automation 3 ขั้น:
    1. myTopology.yaml นิยาม node (ชื่อ, OS, type เช่น 7220 IXR-D5), link (local/remote node+interface), label (role: leaf/spine/super-spine/border-leaf; link: interSwitch/edge/compute/storage)
    2. kubectl -n eda apply -f myTopology.yaml → สร้าง TopoNodes/TopoLinks/Interfaces + digital sandbox
    3. kind: Fabric ใช้ label selector + systemPoolIPV4 + underlayProtocol EBGP + asnPool + overlayProtocol EBGP (+ ISL unnumbered: IPV6) → EDA หา role, generate + push config
  • Fabric resource แตกเป็น DefaultRouter (= network-instance default), DefaultInterface, DefaultBGPGroup/Peer, Policy, (iBGP → RouteReflector/Client) → รวมเป็น NodeConfig ต่อ node
  • Virtual network: ระบุ workload interface ที่จะเชื่อม → EDA สร้าง L3 router (ip-vrf), L2 bridge domain (mac-vrf), IRB, VXLAN tunnel ให้
    • ID (VLAN, EVI, VNI, tunnel index) จัดสรรจาก pool
    • resource: BridgeDomains, BridgeInterfaces, IRBInterfaces, Routers, RouterInterfaces, VLANs, StaticRoutes, BGPGroups/Peers, RoutingPolicies/PrefixSets
  • Transactions: รวมหลาย change เป็น transaction เดียว — fail ส่วนใดส่วนหนึ่ง = rollback ทั้งหมด
    • สำเร็จแล้ว เขียนลง EDA git repo
    • dry run + Diffs ก่อน commit
    • transaction log action:
    • Summary
    • Revert (undo เฉพาะ transaction นั้น ด้วย transaction ใหม่)
    • Restore (คืนทุก resource กลับไปสถานะ ณ transaction นั้น)
  • Deviations: EDA ใช้ gNMI on-change telemetry เฝ้า
    • config ที่ไม่ตรง intent (เช่น แก้ด้วย CLI เอง) = deviation
    • Accept = intent ถูกอัปเดตตาม node
    • Reject = node ถูก revert กลับเป็น intent
  • Observability:
    • dashboard (cluster, node sync, interfaces, alarms, traffic, top interfaces), fabric/service/component state
    • alarms แบบ stateful (probable cause + remedial action; acknowledge/suppress/delete หลัง cleared)
    • telemetry ได้ ทุก YANG data: faults/stats, platform, interface, LLDP, BGP, RIB/FIB
    • ต่างจาก SNMP polling — subscribe ครั้งเดียว ส่งเมื่อเปลี่ยน → scale ดี
  • Queries:
    • EQL (EDA Query Language, คล้าย Jira QL) — ใช้ YANG path เช่น .namespace.node.srl.interface fields [...] where (oper-state = "up") order by [ifindex]
    • normalized query ผ่าน EDA resource = multi-vendor
    • Natural Language Query ผ่าน OpenAI API (ต้องตั้ง API key ใน EngineConfig) และ EDA แสดง EQL ที่ render ให้ดูเสมอ

FSS (Fabric Services System) — รุ่นก่อนหน้า EDA

  • แนวคิดเดียวกัน: fabric intent แบบ declarative YAML, cloud-native (Kubernetes), integrate กับ CMP
  • digital sandbox ใช้ emulate/validate (ไม่ใช่การแจ้งเตือน performance)
  • telemetry แสดงในบริบทของ intent
  • ประโยชน์ = ทำ design/deploy/operate ให้ง่ายและอัตโนมัติ (simplified provisioning/management, orchestration, scale/flexibility)

เทียบ SR OS: ฝั่ง SR OS ใช้ NSP ทำ intent-based automation/assurance (NSP ใช้ YANG/NETCONF/gNMI เหมือนกัน); EDA เน้น DC + Kubernetes-native + digital twin ด้วย containerized SR Linux (ซึ่ง SR OS มี SR-SIM คล้าย ๆ กัน)

ภาคผนวก — แนวคิดทั่วไปที่ควรรู้

  • 3 planes:
    • Data plane = process/forward packet ตาม forwarding table (FIB) — ASIC/XDP บน line card
    • Control plane = routing protocol แลก/คำนวณ routing info เพื่อสร้าง forwarding table (BGP/OSPF/IS-IS, policy) — บน CPM
    • Management plane = การ config/operate/monitor ระบบโดยรวม (mgmt_svr, CLI, gNMI, JSON-RPC, app_mgr ดู health, mgmt interface mgmt0)
  • ไม่มี component ชื่อ "Fabric Manager" ใน SR Linux — งาน orchestrate fabric เป็นของ EDA (หรือ FSS รุ่นก่อน)
  • ความสามารถ "เพิ่ม protocol/feature เป็น app/plug-in" มาจาก modular application architecture + app_mgr + NDK (ไม่เกี่ยวกับ plane ใด)
  • จุดเด่น SR Linux เทียบ NOS เดิม:
    • open/programmable/model-driven
    • unmodified Linux kernel
    • telemetry ในตัว
    • protocol stack จาก SR OS
    • extensible (NDK, CLI plugin)
    • ลดภาระการบริหารจัดการด้วย automation/programmability
  • Monitoring tools:
    • Syslog (logging/event)
    • gNMI streaming telemetry (real-time)
    • SNMP (read-only polling)
    • sFlow (flow sampling)

สรุปย่อหน้าเดียว

Fabric / BGP design

  • Clos: leaf ต่อ spine ทุกตัว, L3 + ECMP, ไม่มี STP, east-west path คงที่, scale ด้วย super-spine
  • eBGP-only (RFC 7938), private ASN 64512–65534 / 4-byte 4.2B–4.29B
  • ASN: leaf ไม่ซ้ำ, spine ใน cluster เดียวกันซ้ำ, spine ต่าง cluster ต่าง, super-spine ซ้ำกันเอง
  • BGP mandatory: ASN + router-id + afi-safi + peer-as + neighbor/group (multipath ไม่ mandatory)
  • ebgp-default-policy import/export-reject-all = true (RFC 8212)
  • default: multipath 1, local-pref 100, pref eBGP/iBGP 170, hold 90/keepalive 30/connect-retry 120/MAI 5s, BFD off, fast-failover on, rapid-withdrawal off
  • RIB: RIB-In-pre → import → RIB-In-post → Loc-RIB (best → RTM) → export → RIB-Out
  • local-pref สูงชนะ → ECMP หาย; prepend ASN ทำให้ peer ไม่ชอบ path
  • BFD: enable ที่ bfd subinterface + failure-detection enable-bfd true; หน่วย µs

CLI

  • modes: running (default, read-only) / state (config+oper) / show (report) / candidate (แก้ได้อย่างเดียว); enter <mode>
  • candidate: shared (default) / exclusive (บล็อกคนอื่น) / private (gNMI/JSON-RPC ใช้; baseline+candidate)
  • prompt: * ยังไม่ commit, + running ≠ startup, ! running ≠ baseline (private)
    • baseline diff (running vs baseline) / baseline update
  • commit now|stay|save|validate|confirmed [timeout] (default 600s) → commit confirmed accept
  • checkpoint: 0 = ใหม่สุด, max 10 (1–255), revert ได้ทุกอัน (ต้อง candidate), auto-checkpoint off
  • startup /etc/opt/srlinux/config.json → rescue → factory
  • idle timeout 300s (0=off), alias {p} required / {} optional, environment save home → ~/.srlinuxrc

Interfaces / NI

  • subinterface index 0..9999, VLAN 1..4094, หลาย subif ต้อง vlan-tagging, type default routed, 16 IPv4+16 IPv6, primary = IP ต่ำสุด
  • LLDP: 802.1AB, default on, hello 30s, hold-multiplier 4, ไม่ใช่ fast failure detection
  • LAG: static default; LACP (admin-key, system-id) block miswire; SLOW 30s / FAST 1s
  • NI: default (ต้องชื่อ default, ไม่สร้างเอง), ip-vrf, mac-vrf; mgmt = ip-vrf (factory)
  • IRB: irb0..255, L3, no VLAN, ตั้ง MTU ได้, mac-vrf มีได้ 1 IRB
  • pref: local 0, static 5, OSPF 10, IS-IS 15/18, BGP 170; ECMP 64 (static 128)
  • MAC: aging 300s, limit 250, MAC dup 3 min / 5 moves / 9 min / stop-learning
  • dup action:
    • stop-learning (intf up, src dup ที่อื่น drop)
    • oper-down (intf down, dst drop)
    • blackhole (intf up, src+dst drop)
  • static: blackhole อยู่ใน NHG, metric 1, pref 5, resolve true, generate-icmp false
    • ECMP = hash % N (ไม่ใช่ round-robin), hash-seed กัน polarization

EVPN-VXLAN

  • VXLAN: UDP 4789, VNI 24 bit, src port = flow hash, outer IP = VTEP
  • EVPN = AFI 25 / SAFI 70
    • RT1 A-D (MH aliasing/mass-withdraw)
    • RT2 MAC/IP
    • RT3 IMET (discover VTEP + flood list, IR)
    • RT4 ES (DF)
    • RT5 IP-prefix
  • IMET มี RD, originating IP, RT, tunnel type IR, VNI — ไม่มี flooding list
  • RD auto = system0-IP:EVI, RT auto = AS:EVI (ตั้งเองเพราะ leaf ASN ต่างกัน)
  • ESI global unique, 0 = single-homed; SR Linux VXLAN MH = all-active (host ใช้ LAG)
  • workflow: system0 → EVPN iBGP group (afi-safi evpn, local-as, RR ได้) → bridged intf → vxlan-interface (VNI เดียวกันทุก VTEP) → mac-vrf bgp-evpn/bgp-vpn
  • Asymmetric = mac-vrf ทุก leaf, RT2/RT3, ingress หลาย lookup/egress L2
  • Symmetric (IFL) = routed vxlan ที่ ip-vrf, RT5, scale ดีกว่า

Logging / ACL

  • logging = rsyslog, /etc/rsyslog.conf
    • destinations: file / buffer (RAM) / console / remote-server (UDP/TCP 514)
    • sources: facility / subsystem / filter (console ไม่ใช่ source)
    • SR Linux = local6; ไม่มี encrypted local file
  • default: buffer messages (local6 ≥ info), buffer system (อื่น ๆ ≥ warning), file messages (local6 ≥ warning)
  • debug = priority debug + trace-options
  • ACL order: System → Ingress → Capture → CPM → Egress; default action accept; seq 1..65535 first-match
  • cpm-filter = control-plane protection (DoS), apply ที่ system control-plane-traffic input
    • rate-limit ได้: policer = per-linecard HW (kbps/bytes), system-cpu-policer = CPM SW รวมทุก LC (pps/packets)
  • capture-filter = copy ทุก subif ingress → tools system traffic-monitor (header 48 byte)
  • ต้องการ match outer VXLAN ที่ terminate = system ACL

Users / mgmt / ZTP

  • users: SR Linux (UID≥1500) / Linux (1000–1499) / TACACS+ (random UID); PAM + aaa_mgr; role = read/write/deny
  • TLS profile สำหรับ gNMI/JSON-RPC
    • subject สร้าง key pair เอง → CSR → CA เซ็นด้วย CA private key
    • trust-anchor = CA ของ client cert; authenticate-client default false
  • ZTP: grub.cfg autoboot flag → DHCP → option 66/67 หรือ 43 → download+run Python script → app_mgr
    • log /var/log/ztp; สำเร็จลบ flag; retry 3 → reboot
    • ZTP พื้นฐาน ไม่มี PKI/CSR

EDA

  • Kubernetes Operator (ไม่ใช่ Docker Swarm), intent-based ทุกด้าน Day 0/1/2+
  • digital sandbox = emulate/validate เร็ว+ประหยัด
  • fabric intent = YAML ข้อมูล minimal → auto deploy (ไม่เก็บ telemetry)
  • transaction all-or-nothing + git, deviation accept/reject
  • observability = gNMI telemetry, EQL + NL query (OpenAI)
